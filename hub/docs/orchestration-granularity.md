# 编排粒度对比：从自然语言到状态机

这份文档回答一个问题：LangGraph 那种细粒度的编排，对我们有没有必要？

结论先说：**不是所有场景都需要，但我们的文档格式里有几处明确的空白，值得补**。细粒度是工具，不是目标；用在需要的地方，其余地方用自然语言描述反而更好维护。

---

## 一、编排粒度谱

把"描述一个多智能体协作流程"的方式，从粗到细排成一条谱：

| 粒度 | 代表形式 | 描述的是什么 | AI 执行保障 | 人工维护成本 |
|------|----------|------------|-------------|-------------|
| 1 — 自然语言 | "帮我做一个技术调研" | 意图 | 最低，靠模型推断 | 极低 |
| 2 — 结构化文档 | 我们的 `agents.md` / `process.md` | 角色 + 流程骨架 | 中等，有结构但语义仍开放 | 低 |
| 3 — 消息协议 + SOP | AutoGen 对话协议、AgentScope SOP | 消息格式 + 文字流程约定 | 中高，格式固定但逻辑仍有模糊 | 中 |
| 4 — 类型化状态机 | LangGraph State Schema + Conditional Edge | 节点、状态结构、分支条件 | 高，类型错误在运行前可检测 | 高 |
| 5 — 手写图代码 | Python 手写 NetworkX 图 + 测试 | 完整执行拓扑，图灵完备 | 最高，完全确定性 | 最高 |

我们目前在粒度 2，有些场景需要 3 的能力，极少数场景需要 4。粒度 5 对我们没有必要——那是"不用 AI 执行器、完全手写逻辑"的领域。

---

## 二、LangGraph 的四个核心抽象，我们各怎么看

### 2.1 状态模式（State Schema）

**LangGraph 怎么做**：每个节点接收和输出一个有类型的结构体（TypedDict / Pydantic）。节点之间传的是状态快照，字段有类型约束。

**我们现在有什么**：`doc`（共享文档）描述的是团队共享的知识资产，是"有哪些文档、谁能看"，不是"节点之间实际流动的数据结构"。

**有没有必要**：**对大多数场景没有必要**。我们的系统里智能体之间传的是自然语言内容（消息、报告、审核意见），不是结构化的状态对象。强制定义 State Schema 反而让编排文档变成代码。

**例外场景**：当一个工具链需要精确的字段传递时（比如调研员输出一个事实表，审核员按固定字段审核），可以在 `doc` 的 `format` 字段里描述预期结构，这已经足够。不需要引入类型系统。

**结论**：不引入，但在 `doc` 定义里加 `format` 字段留口子。

---

### 2.2 条件边（Conditional Edge）

**LangGraph 怎么做**：节点执行完后，一个 Python 函数检查状态，决定下一步走哪个节点，可以扇出到任意多条路。

**我们现在有什么**：`gate` 有 pass / fail 两条路，decider 是 human / rule / agent 三种类型，但判断逻辑是自然语言描述（`decider_text: "调研来源不少于 5 个"`），不是可执行的条件。

**有没有必要**：**有，但不需要 Python 函数，用扩展的 gate 定义就够**。

我们的 gate 现在只有两条出路。真实情况更复杂：审核员可能打回某一路调研而不是整个阶段，编排者可能根据质检结果选择不同的修复路径。这些都是"多条出路"的场景。

**补充方案（轻量，不引入代码）**：

```markdown
## @gt_research [gate]
after_stage: s_research
decider_type: agent
decider_who: n11
paths:
  - condition: 所有来源均可信且覆盖约束
    next: s_debate
  - condition: 部分来源样本量不足但数量达标
    next: s_debate
    note: 带风险标注进入辩论
  - condition: 来源数量不足 5 个
    next: s_research
    note: 打回补充
```

`paths` 替换原来的 `pass/fail`，每条路有自然语言条件和 `next`。AI 执行时读这个做判断，不需要代码。

**结论**：把 gate 的 `pass/fail` 扩展成 `paths: [{condition, next, note}]`，这是我们文档格式里值得补的一处。

---

### 2.3 循环与回边（Cycles）

**LangGraph 怎么做**：图里允许有环，ReAct 的"思考→工具→观察→再思考"就是一个显式回边，而不是靠外层重试。

**我们现在有什么**：`scenario` 里的 `rework`（被打回重做）是在运行场景层表达的，process 结构本身是 DAG。

**有没有必要**：**需要在 process 层显式表达，而不是只在 scenario 层**。

gate 的 `fail: s_build` 本质上就是一个回边——但现在它被编码在 gate 定义里，process 图看起来像 DAG，其实有隐含的环。这没有问题，只是需要在文档里明确说"gate 的 fail 路径就是回边，允许环"，避免解析器把 process 当成严格 DAG 来验证。

**结论**：在 process.md 的格式说明里加一句注释，说明 gate 的 fail 路径形成回边，这是设计意图，不是错误。不需要改格式。

---

### 2.4 持久化检查点（Checkpointing / HITL 暂停点）

**LangGraph 怎么做**：流程在 HITL 节点暂停，序列化到数据库，等人工审批后从断点恢复。状态持久化是框架内置的。

**我们现在有什么**：`decider_type: human` 说明这里需要人工决策，但没有描述暂停-持久化-恢复这个机制。这是执行层的问题，不是文档格式的问题。

**有没有必要**：**文档层不需要，执行层需要**。

文档描述的是"这个 gate 需要人工决策"，至于怎么暂停、怎么通知人、怎么恢复，是执行框架（实际运行这些智能体的系统）负责的事，不应该写进编排文档。写进去反而把文档和特定的执行框架绑死了。

**结论**：不在文档里加这个抽象。执行框架读到 `decider_type: human` 自己处理持久化。

## 三、我们的文档格式有哪些实际空白

汇总上面的分析，真正值得补的地方只有两处：

**空白 1：gate 支持多条出路（不只是 pass/fail）**

现在：

```markdown
pass: s_debate
fail: s_research
```

补充后：

```markdown
paths:
  - condition: 来源数量 ≥ 5 且均可信
    next: s_debate
  - condition: 来源数量 ≥ 5 但有风险
    next: s_debate
    note: 带风险标注
  - condition: 来源数量 < 5
    next: s_research
```

`pass/fail` 作为简写仍然有效（解析器把它们翻译成两条 path），新格式向前兼容。

**空白 2：个体的"输出格式"可以有轻量描述**

当一个智能体的输出需要被下游解析（不只是阅读）时，可以在 agent 定义里加 `output_format`：

```markdown
# @n11 [individual] #role/reviewer #phase/research
output_format: 审核意见表（来源 id、风险等级 low/medium/high、是否可信、备注）
```

这不是类型系统，只是给 AI 执行时的格式约定，也给人工阅读文档时一个明确的预期。

## 四、哪些场景需要粒度 4（LangGraph 级别），哪些不需要

| 场景 | 需要的粒度 | 理由 |
|------|-----------|------|
| 多智能体深度调研、辩论、质检 | 粒度 2，偶尔 3 | 智能体之间传的是自然语言内容，不需要类型约束 |
| 需要精确字段对齐的工具链（事实表、接口约定） | 粒度 2-3（用 output_format 字段描述） | 有格式约定就够，不需要运行时类型检查 |
| 实时监控 + 自动响应（如 incident_war_room） | 粒度 3-4 | 触发条件需要精确，可以加 `trigger_condition` 字段 |
| 金融交易、安全合规等零容错场景 | 粒度 4-5 | 这类场景根本不该用 AI 编排，应该用代码 |
| 纯代码生成 / 工具调用链 | 粒度 4（直接用 LangGraph 或类似框架） | 这不是我们的场景，我们做的是"智能体协作"不是"函数管道" |

**一句话结论**：LangGraph 的细粒度对我们绝大多数场景没有必要。它解决的问题是"函数管道的精确控制"，我们解决的问题是"有意图的智能体的协作"。两个不同的问题域，不需要用同一个粒度描述。我们需要的是在现有格式上补几个字段，不是引入状态机。

## 五、各编排工具的粒度定位（参考）

| 工具 | 主要粒度 | 核心抽象 | 适合的场景 |
|------|---------|---------|-----------|
| 自然语言 prompt | 1 | 意图描述 | 单次任务、简单请求 |
| 我们的 hub/cases/ 文档 | 2 | 角色 + 流程 + 决策 | 多角色协作，重在理解和可视化 |
| AutoGen | 2-3 | 对话模式（two-agent / group chat） | 对话式协作，灵活但难以追踪 |
| AgentScope | 2-3 | Message + Pipeline + SOP | 结构化对话，SOP 接近我们的 process |
| CrewAI | 2-3 | Agent + Task + Crew | 角色分工，但流程控制较弱 |
| LangGraph | 3-4 | State Schema + Conditional Edge + Cycles | 精确控制的工具链和 ReAct 循环 |
| Prefect / Dagster | 4-5 | DAG + 数据流 + 调度 | 数据管道，不适合 AI 智能体 |
| 手写代码 | 5 | 图灵完备 | 零容错、完全确定性场景 |
