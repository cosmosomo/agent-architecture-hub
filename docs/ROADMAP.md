# 后续开发计划

> **历史文档**（截至 10-13：观察台阶段的开发计划。现在的目标和下一轮候选见 [channels/演化路径.md](../channels/演化路径.md) 最后一节。）

这份计划写的是**已经看清、还没做**的事，按依赖和价值排序。每一项都写了现状、要做什么、做到什么算完成。已经做完的不在这里（见 `README.md` 和 `docs/ARCHITECTURE.md`）。

English summary: (1) one Trace — the standalone viewer and the observatory share one component, one link format and one annotation source; (2) one orchestration and visualisation layer — layout, default views and edits live in the case and write back to its documents; (3) facts from annotated sessions, compared with the written definition; (4) parsing with machine verification; (5) release engineering.

## 1. Trace 的统一

**现状。** 有两个入口看同一份会话：独立的 Trace 查看器（`/trace/`）和观察台里的运行明细。它们用的是同一个组件（后者是前者的单文件构建 `hub/vendor/hub-trace.js`），两边已经能互相跳到同一个步骤（`#s=<会话>&n=<步骤>` 和 `#c=tree:<根>&j=<会话>&n=<步骤>`）。但状态是各管各的，而且**决策层只有观察台有**：决策日记写在案例文档里，由观察台的解析器读，独立查看器读不到。

**要做的：**

1. **一个标注来源。** 把决策日记编译成契约里的标注集文件（`annotations/<生产者>/<会话>.json`，契约早已按“可重算、各生产者各存一份”设计），由本地服务提供 `GET /api/annotations/<会话>`。观察台和独立查看器都从这里读，不再各读各的。编译由命令行完成（`hub-trace annotate <案例>`），解析器（`from-docs`）和服务共用同一段读日记的代码，放进共享包。
2. **一个链接格式。** 现在两边的参数名不同（`s`/`n` 对 `c`/`j`/`n`）。合成一套：会话、步骤、粒度、对照方式，任一页面都能读写，链接在两边互通，不需要转换。
3. **一个状态。** 选中的步骤、粒度、主题在两个页面之间共享（同源的 `BroadcastChannel`），在一个页面里选中，另一个页面跟着走。
4. **互相知道对方。** 独立查看器里，一个会话如果是某个案例的根会话（或被某个案例标注），显示“出现在案例 …”并链到观察台；观察台里一个案例的会话链到查看器（已有）。
5. **决策层的生产者。** 日记现在只能手写（生产者 `human`）。加规则生产者（按轮切段，触发是用户消息或上一步结果，选择是这一轮实际做的调用，理由取模型推理摘要；做不出“备选”），再加智能体生产者（见第 4 节），三者走同一个标注集格式，页面上可以并排对照不同生产者的版本。

**完成的标准：** 在独立查看器里打开一个被案例标注的会话，看到和观察台完全相同的决策层；在任一边选中一步，另一边打开时停在同一步；新增一个生产者不需要改任何页面代码。

## 2. 编排层和可视化层的统一

**现状。** 编排（案例文档、hub-graph）是页面的**只读输入**；可视化的状态散在几处：观察状态在地址栏里，手动挪动的卡片位置和“我的视图”存在浏览器的 `localStorage`，一个案例打开时的默认样子写在代码里（例如示例团队默认只看定义）。画布上能拖、能选、能点操作，但结果不会回到文档里；换一台机器、换一个人打开同一个案例，看到的是另一个样子。

**要做的：**

1. **布局和默认视图属于案例。** 手动挪动的偏移（`HUB.obsDrag` 已经是 `{key: [dx, dy]}` 的纯数据）、案例的默认视图、折叠状态，写进案例自己的文件（`layout.md`，或 hub-graph 里已经预留的 `view` 段），随案例一起进 git。页面打开案例时先读它，再用浏览器里的覆盖。代码里写死的“按案例类型决定默认对照方式”改成案例自己声明。
2. **画布上的编辑写回文档。** 先做最小闭环：改名、改分组、增删一条关系、改一个关卡的出口。写回用**保留原文的补丁**（不重排、不丢注释和不认识的字段），写完用同一个解析器重新读一遍验证，撤销靠 git。
   - 这要求服务从“只读”变成“可写”。**默认仍然只读**；写回要显式打开（`npm start -- --write`），只允许改 `hub/cases/` 下的文件，请求必须带本次启动时生成的令牌并通过 `Origin`/`Host` 校验，路径穿越检查沿用现有的。
3. **一套词汇。** 视图、线的类型、粒度、对照方式现在在代码里、`view` 段里、地址栏里各有一套写法。统一成格式规范里的一套（`docs/hub-graph-format.md`），解析器、地址栏和写回都用它。
4. **概念画板接成编写入口。** `/concept/` 是独立的拖拽式设计器，数据不共用。先做单向：把画板里搭好的团队**导出成案例文件夹**（agents、groups、process 的 md），放进 `hub/cases/` 就能在观察台里看。设计和观察不再是两个产品，是同一份文档的两个入口。双向以后再说。
5. **节点类型由数据决定怎么画。** 现在加一类卡片要在 `HUB.obsCards.extra` 里写模板；把常见的（标题、徽标、几行字段）做成声明式描述，格式里的 `type` 直接映射，少数需要自定义画法的才写代码。

**完成的标准：** 在画布上挪一个部门、改一个关卡的出口，保存后 `git diff` 只有这两处改动，重新打开页面和原来一样；另一台机器拉下仓库，打开同一个案例，布局和默认视图一致。

## 3. 事实：用标注的会话对照写下来的编排

**现状。** md 里的个体可以标注它跑成的会话（`session:`），根会话和决策日记也已经接上，但这些**只用来打开 Trace**。案例的事实仍然是模拟的，或来自 `traces/` 里的记录；真实会话没有替换模拟事实，所以“写的”和“发生的”还不能直接对照。

**要做的：**

1. 一个事实提供者（`HUB.facts.register`）：案例带了根会话，就从会话树里读事实——每一轮成为这个个体的一次运行，子智能体的派出成为交接，工具调用成为渠道上的调用——替换模拟值。个体按 `session:` 标注或名字匹配；对不上的成为“编排里没有”的个体，不丢。
2. 匹配规则写清楚、可检查：哪些交接落在任务线上，哪些是“发生了但没写”，体检按 `comparability` 的口径措辞（真实会话是 `written`：只说“与写下来的编排不一致”，不说对方偏离设计）。
3. 案例实例（K1、K2…）和根会话的对应：一个根会话是一次完整的工作；同一个会话里做了几件事时，用决策日记的轮范围划出实例。

**完成的标准：** 给 `feature_sprint` 写上根会话，页面上橙色线、从没派出的个体、没送达的文档来自真实会话，而不是模拟。

## 4. 解析：带机器验证的智能解析

设计在 [parsing-design.md](parsing-design.md)。顺序是：先把验证器独立出来（引用完整、回指检查，先在现有 1141 个案例上跑出一份“哪些是模型写错的”清单），再做一个来源的完整流水线并量指标，然后是修复回路、缓存、更多来源，最后是日志类来源（交给 `trace/` 的适配器先读成契约）。第 1 节的智能体生产者就是这条流水线的一个输出。

## 5. 数据集读取器

`MAST`、`aarch` 的 notebook、`Smallville` 回放、`SOTA` 生产账本的轨迹格式各异，还没有读取器，案例仍走模拟。每个读取器是 `HUB.fromTraces.readers` 里的一项，按案例的 `source:` 匹配；以原始数据集为准、按确定性规则读，不交给模型。

## 6. 体验和视觉

- 默认只点亮主线、其余变淡；每个视图顶部一行摘要（已有部门条，其余视图补齐）。
- 大案例（几百个个体）的性能：分层绘制、视口外不画、连线合并。
- 界面文字现在是中文；文案抽出来，加英文界面。
- 键盘可达性：画布上的卡片可用方向键移动选中，`Enter` 展开。
- 浏览器端到端冒烟测试（打开每个视图、点开一次运行、拖一张卡片、切主题）进 CI，并用它重生成 README 里的截图。

## 7. 工程和发布

- 合并到 `master`、打版本标签、写发布说明。
- `npx` 一行启动：把服务打成可直接运行的包。
- 托管演示页：页面需要服务，纯静态托管跑不起来；可以做一个内置示例案例的**快照构建**（预先算好的 JSON），只用于演示，与正式使用的服务分开。要不要做，取决于是否需要公开链接。
- 依赖更新和许可清单：随构建生成第三方许可列表（AgentPrism 等）。

## 先后顺序

1 的第 1、2 步和 2 的第 1 步互不依赖，可以先做，它们解决的是“两个入口各看各的”和“布局不跟着案例走”。2 的写回依赖 2 的第 1、3 步（先有统一的词汇和落盘的布局，再谈改文档）。3 依赖 1 的第 1 步（先有统一的标注来源）。4 和 5 可以随时穿插。
