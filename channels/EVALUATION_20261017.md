## 一、一句话结论

下层（各家原生接口和 ACP 桥）能做的事比我们以为的多，我们的网关和页面却只用了其中最窄的一条路（acpx 命名会话），其余能力用“发一段文字”去模拟，于是出现了大量名不副实的按钮；而页面显示什么，又是写死在代码里的，不看实测。

## 二、缺陷按根因归类（不是按症状罗列）

**最重的一条（L2-A 实测，黑板 896～909 行）**：经 :8899 的 `/api/gateway/send`，七家里只有 Antigravity 能从新建一路跑到恢复（恢复时复述了第一轮暗号）。其余六家：Codex 新建就失败（ensure 没建成会话）；Claude、OpenCode、Hermes 跑了 60～250 秒没有回复；ZCode、WorkBuddy 智能体其实回复了，网关仍判失败；恢复都在 0.3 秒内返回空回复，像是排进了网关内存队列而没有执行。对原生会话发消息被分到 acpx 会话 `hub-zcode`。也就是说，**现在的控制台对 acpx 系六家，最基本的“新建会话、恢复会话”都不可靠**；下层 acpx 命令行本身是通的（矩阵 L1b），断在我们的网关（完成判据、超时 180 秒、ensure、队列）。具体原因待逐条定位。

### R1 没有能力登记：显示什么、走哪条路都是写死的
- 现象：两个前端各有一套写死的模型表和能力开关；网关的 `CHANNEL_PROFILES` 也写死能力声明。真能切模型的 Codex、Hermes 在首页抽屉里不给入口，做不到的却照样显示（INTERFACES 缺陷 12）。
- 根因：《核心抽象》§2.8 要求“每个渠道声明能力标记，每项标明已实测或只声明”，系统里一直没有这张表，现在矩阵才第一次把它测出来。

### R2 控制只有一条路，其余原语用文字模拟
- 现象（全部经实测或读代码确认）：
  - 续跑 = 发一句固定提示；接力/分叉 = 最近 3 轮文字拼成提示发给新会话；
  - 审批 = 进程结束后正则匹配输出，再带 `--approve-all` 重发；
  - “中断并发送” = 先取消再新开一轮，不是插话；
  - 排队在网关内存里，重启即丢。
- 下层其实能做（矩阵）：轮内插话（Codex app-server、Antigravity）；原生分叉（Codex、Antigravity、ZCode/Hermes/Claude ACP 桥）；一轮中途的真审批（Codex app-server、Claude/ZCode/Hermes ACP 桥）；接管原生会话（Claude ACP 桥、Codex app-server、Antigravity RPC）。网关一个都没接。
- 根因：网关以“acpx 命名会话”为唯一控制面（Antigravity 除外），没有“按家和入口选路线”的结构。

### R3 读和控是两套会话身份
- 现象：左栏显示的是各家原生会话（读层），对它发消息时网关拿编号末段当 acpx 会话名，新建了一个同名空会话，原会话没续上（接错路）。
- 根因：会话的身份没有统一成“家 + 入口 + 原生编号”，acpx 的名字被当成了唯一身份。

### R4 前后端约定散落，后端不校验
- 现象：/console/ 发 `permissionMode`，后端读 `permissions`，下拉框整体无效（实测：选“全部拒绝”文件照建）；两个页面对同一操作走不同接口（续跑、切模型、切目录）；死按钮两个。
- 根因：两套平行的完整前端，各自拼请求；后端对未知字段静默忽略。

### R5 默认值不安全
- 现象：权限默认 `all`；元智能体“自动批准”默认把只读静默升级为全放行，审批横幅在正常使用中走不到；`/api/control` 不调智能体却写仓库文件。
- 根因：安全相关的默认值放在多处，没有“默认最小权限、升级必须显式”的规则。

### R6 运行性质：超时、状态、唤醒
- 现象：:8899 调 acpx 写死 `--timeout 180`，长任务被杀；回复文本翻倍（流和文件轮询双写）；调用方被杀后智能体照样干完，调用方却以为结束了；命令行网关此前有多行截断、1MB 截断（已修）；Antigravity 的“这一轮结束”误判（已修）。
- 根因：“观察”和“这一轮结束”的判据没有按家定义，混用进程退出、输出文本、文件轮询；唤醒和卡住检测在网关里不存在。

### R7 能力渠道层不在系统里
- 现象：中转余额不足、渠道认证失败、模型 503、凭证过期，都在实测中撞上，系统里看不到也选不了。
- 已有设计：《生态接入_CCSwitch_20260929》——中枢只读 cc-switch，按调用用单次覆盖换渠道（接入面 D，读 key 前须用户确认，尚未确认）。

## 三、设计方案（待确认）

总原则：重构不重写；实测矩阵是唯一的能力真源；每步小、可测、可回退。

1. **能力登记表**：由黑板生成 `capabilities.json`（家 × 入口 × 能力 → 已实测通/断/未验证 + 证据行号）。网关和两个前端都只读它，不再各自写死。对应 R1。
2. **网关按能力路由**：每个原语一张实现表，按（家，入口）选下层路线；登记表里没有的，接口明确返回“不支持”，页面不显示。第一批接三条高价值路线：Codex app-server（插话、分叉、真审批、压缩上下文）；ACP 桥直连（Claude、ZCode、Hermes 的真审批和接管原生会话）；Antigravity Connect-RPC（分叉）。对应 R2。
3. **会话身份统一**：一个会话 =（家，入口，原生编号）；acpx 名字只是入口之一。对原生会话发消息，按登记表选恢复路线（ACP `loadSession`、app-server `thread/resume`、`agentapi send-message`、命令行 `--resume`），做不到就标只读。对应 R3。
4. **一套前端约定**：抽出一个共用的请求模块给两个页面用；后端校验字段、拒绝未知字段；页面按登记表条件渲染；按“唯一真值入口”把约 60 组控件收敛到约 10 组（外观不动，删重复与死按钮）。对应 R4。
5. **默认安全**：默认只读；升级权限必须用户显式选择并在页面可见；元智能体不得静默升级；`/api/control` 停止写仓库。对应 R5。
6. **运行性质**：超时可配、默认放长；排队落盘；去掉双写；“这一轮结束”按家用实测判据（Antigravity 用会话索引；acpx 系用本轮结束帧）；网关加卡住检测和唤醒。对应 R6。
7. **能力渠道**：先只读接入 cc-switch 目录与用量（不碰 key）；按调用换渠道等用户确认接入面 D。对应 R7。

### 7.1 逐项对照：我们的抽象 × ACP 协议 × acpx 运行时（2026-10-17，读 acpx 0.19.5 runtime.d.ts 与《核心抽象》§6.1 后写）

用户指出：“你好像没有细致比照我们现在的抽象和acpx现在的抽象的功能……没研究透就开始替换了”。P3 已叫停（Codex 未改任何文件），先做这张对照。纲目用《核心抽象》§6.1 已定的“六个网关模块”和“六个标准工具”，不另起。

| 我们的抽象（核心抽象 §2、§6.1） | ACP 协议 | acpx 运行时 | 判断 |
|---|---|---|---|
| 智能体登记（Agent Registry）+ 能力标记（§2.8，契约四档位图） | `initialize` 的 agentCapabilities | `createAgentRegistry`、`inspectAgentModels`、`AcpRuntimeCapabilities.controls`（只有 set_mode、set_model、set_config_option、status 四项） | 部分等价：它只登记 ACP 能控的四项；我们的四档位图 + 实测证据更宽，保留我们的 |
| 会话（Session）与身份 | `session/new`、`session/load`/`resume` | `ensureSession({sessionKey, agent, mode: persistent|oneshot, resumeSessionId, cwd})`；会话记录存 ~/.acpx | 等价，借用。`resumeSessionId` 可接原生会话（xacpx /ssn 即此），但要该家桥支持加载 |
| 轮 / 作业（Run、Job） | `session/prompt` | `startTurn`/`runTurn`，结果三态 completed / cancelled / failed，带 stopReason | 等价，借用。直接替代我们“进程退出 + 猜”的完成判据 |
| 事件流（观察·实时） | `session/update` | 事件 text_delta（输出/思考）、status（含用量 used/size）、tool_call、done、error | 等价，借用。替代我们解析 NDJSON + 轮询文件（翻倍问题的根） |
| 状态识别（三状态 + 待命属性） | 无统一状态方法 | `getStatus`：记录编号、后端会话、模型、用量、可用命令；没有“工作中/等回应/让出/在等什么” | 部分：它给不了待命属性和“在等什么”，这部分是我们的（唤醒议题） |
| 打断 | `session/cancel` | `cancel(handle)` | 等价，借用 |
| 关闭会话 | 无标准方法 | `close(handle)`（本地关闭） | 等价，借用 |
| 回应（审批，Approval Manager） | `session/request_permission` | `onPermissionRequest` 回调 + permissionMode / permissionPolicy（含 escalate）/ nonInteractivePermissions；另有 `onElicitation`（向人提问） | 等价，借用；替代我们的正则审批。向人提问对应我们“人在环” |
| 插话 | **无**（类型注释原文：ACP 没有轮内插话请求） | prompt mode `steer` 不改变当前轮，共享运行时直接拒绝 | **不能借**：真插话只有 Codex app-server `turn/steer`、Antigravity send-message（实测），要我们的原生驱动 |
| 分叉 | `session/fork`（unstable，各桥支持不一） | **无** | **不能借**：走 ACP 原始请求（ZCode、Hermes、Claude 桥实测可）或原生（Codex app-server、Antigravity RPC） |
| 压缩上下文 | 无标准方法 | 无（靠会话内发 /compact） | 我们自己按家处理 |
| 切模型 / 切模式 | `session/set_model`、`set_mode`、`set_config_option` | `setModel`、`setMode`、`setConfigOption`；不支持时抛 RequestedModelUnsupportedError | 等价，借用；效果仍要按家用本地记录核验（矩阵） |
| 查额度（渠道级） | 无 | status 事件里有 used/size（上下文用量），不是账号额度 | **我们的**：渠道层 |
| 排队 | 无 | 共享运行时的会话主进程负责排队 | 等价，借用；替代网关内存队列 |
| 工作区（Workspace Manager） | cwd | cwd | 等价；worktree 隔离是我们的 |
| 唤醒、看护、协作、人在环、产物 | 无 | 无（flows 是写死脚本） | **我们的** |

## 八、在基线之上我们做什么（用户 2026-10-17：“我们的系统应该有功能比acpx做的更多吧，功能更多是我们应该做到的”）

acpx 是“用 ACP 控制一个会话”这一层的地基，借用它把新建会话、恢复会话、打断、审批做稳（P3）。我们的价值在它上面：

| 我们多做的 | acpx 的边界 | 对应设计 |

| 接入不走 ACP 的智能体：Antigravity agentapi 与 Connect-RPC（插话、分叉）、Codex app-server（插话、分叉、压缩上下文）、桌面端 | 只管 ACP；antigravity 在其注册表里调不起来 | 能力层 |
| 读与控统一会话身份，看见并接管原生会话、子智能体 | 只管自己建的命名会话 | R3、P2 |
| 实测能力登记表，页面按实测显示 | 不提供“哪家哪项真能用” | 核心抽象 §2.8 |
| 能力渠道：按调用选中转与 key、额度、健康、熔断，回答“下一个是谁” | 只有一个模型参数 | 能力渠道层、接入面 D |
| 唤醒与看护：在等什么、到了叫醒、卡住发现 | 只有一轮的结束与取消 | 第六节唤醒议题 |

原则：地基能借就借（acpx、xacpx 的做法），力气花在上面这些层。
