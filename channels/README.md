## 立体认知：整个体系的语言（以此为纲）

本节是全体系共用的语言：别处可以复写、可以拓展，不能和它冲突。它展开的是《核心设计总览》三个核心层（信息、智能体、能力渠道）在“怎么接到各个智能体产品、怎么做给人和智能体用”这一面上的样子。

用户原话（逐字，2026-10-18）：
- “我认为做项目最重要的就是脑子里有个清晰的架构图。……这是原生应用层。然后再往后，会有各家生态的 APP server之类的原生api。这部分它可以被暴露，然后让其他去看到。但这部分暴露的不够，我们要基于我们的理论分析和推导，以及各家生态的探查，去找到更加更全的能力矩阵、基本能力单元。……第 3 层就是适配器，第 4 层就是前端交互应用……然后你得有一个矩阵，知道理论上最多能达成什么样的多少多少层，理论上能做到什么样的情况，然后现状能做到什么情况。……认知上必须能够看到最广，才能够做的高效，而不是重复造轮子，很多东西底层就应该摸清楚。”
- “桌面端不是实测，而是截图分析或者想办法通过代码分析什么的”
- “我们得从做好网页接近原生桌面端的使用体验的角度，反推需要哪些接口能力”
- “一套认知，分层次，有结构地梳理我们完整的架构，分层次的能力，理论极限，如何拓展之类的问题，想清楚”
- “别处可以复写，但是不能有冲突，只能有拓展，是整个文档的语言体系。”
- “你应该清晰地建立立体的认知，然后从立体的认知的角度展开讲这些”
- 总目标（10-18 晚）：“我们的总体目标就是，建立清晰的认知，所有的能力单元，注册表维护，打通闭环，然后稳步拓展，并且建立后续拓展能力（后端多一个功能/产品接到前端完善，测试后端各家产品的实际情况都变得低负担）的清晰架构，然后稳步拓展，最终用所有方法打通尽可能多的能力单元，并且注册，接到我们的前端，最终让我们每一层都能够承载巨量的海量的能力单元，让所有能力单元在我们的架构里清晰可见，可维护，可被调用，最终可被编排”
- 清晰的标准（10-18 晚）：“清晰到什么程度呢？一眼没多少行的文档，就知道如何调用各家各层能力，如何维护，出bug如何处理。管线要非常清晰，没有什么冗杂的东西”

### 一个对象，四根轴

我们研究的只有一样东西：**智能体**，即模型加循环加会话。它跑在持有它循环的**宿主**里，靠**能力渠道**供给模型和额度，把会话记录、产出物留在**信息**（文件）里。关于它的每一条认知，都是这样一句话：某一个产品、在某个位置上、某个尺度的某件事，做到什么程度，凭什么这么说。所以认知落在四根轴围成的空间里：

| 轴 | 刻度 | 回答 |
|---|---|---|
| 尺度 | 一步 ⊂ 一轮 ⊂ 一个会话 ⊂ 两个会话之间 ⊂ 一群会话 | 这件事发生的范围有多大 |
| 位置 | 智能体本体 → 原生面 → 适配路线 → 我们的后端 → 使用者（人用网页，智能体用命令行网关）；另有反方向：智能体经钩子、装进它里面的工具、命令行网关来找我们 | 这件事在哪儿被做到、被看到 |
| 智能体产品 | Claude Code、Codex、Antigravity、ZCode、WorkBuddy、OpenCode、Hermes、Gemini CLI、Droid……。一个产品是同一套循环和会话存储，可以有几个入口（桌面端、命令行、app-server、IDE 插件） | 哪一个产品 |
| 依据 | 推理（理论上限）→ 声明（帮助、协议、文档）→ 观察（截图分析、代码分析）→ 实测（行为证据） | 凭什么这么说 |

**用词**（10-18 词汇巡检，一义一名，和《术语表》“对象与身份”一致）：
- **智能体产品**：上表“产品”这根轴，即《术语表》的“原生智能体产品”。不说“家”（指不出是什么），也不说“厂商”（一个厂商有几个产品，ZCode 跑的模型和 ZCode 本身也不是同一个产品）、“商业 agent”（OpenCode、Hermes 是开源的）。代码里的 `channel`、`family` 参数指的就是它。
- **能力渠道**：只指模型、账号、中转、key 这些供给。代码里叫 `channel` 的是智能体产品，不是能力渠道，读代码时别混。
- **宿主**：只指持有某一级循环的一方。终端、浏览器、产出物所在的地方叫**运行环境**。
- **网页**：人用的那个位置（`m/`，旧的 `/console/` 和首页抽屉）。不说“前端”“控制台”。
- **适配路线**：我们去接一个原生面的办法（acpx、app-server 驱动、Connect-RPC、OpenCLI、直连 CDP）。不说“通道”，免得和能力渠道混。
- **中心**：我们的协作中枢，一群会话这一级的宿主。文档体系里被别处引用的“中心”，在本文叫“语言”，就是这一节。
- **原生面**：智能体产品暴露出来的接口面，即《适配器模块设计》说的“接口面”。“平台”一词不单用：指智能体产品时说产品，指我们时说协作中枢。
- **入口**：进入一个产品的一种具体方式（Codex 的 app-server、Claude Code 的桌面端）；它属于哪一类，看“位置”里的七类原生接口面。

格子里的值用登记表第 2 节的五档（原生、经桥、补齐、不支持、未测），格子的来历用“依据”这根轴。同一个格子上依据不同的话可以同时存在，比如档案卡的声明和黑板的实测，由新证据逐步修正。

### 尺度：同一个结构逐级嵌套

每一级都是同一个形状：送进去，循环，交出来；有状态，有持有它的一方，有外部能进去的时机。

| 尺度 | 循环 | 状态 | 谁持有（宿主） | 外部能进去的时机 |
|---|---|---|---|---|
| 一步 | 一次模型调用或工具调用 | 进行中、完成 | 智能体进程 | 工具调用前后（钩子） |
| 一轮 | 模型 → 工具 → 结果 → 模型，直到交回结果 | 工作中、等回应 | 宿主进程 | 步与步之间（插话、打断）、请求审批时、工具结果返回时、一轮结束时 |
| 一个会话 | 一轮接一轮 | 执行中、待命（热或冷，记着怎么进来的、在等什么）、关闭（《核心抽象》2.2） | 宿主进程 | 一轮开始前（新建、恢复、分叉、压缩、切模型） |
| 两个会话之间 | 派活 → 送达 → 唤醒 → 交回 | 发出、送达、读到、交回（回执，《适配器模块设计》第 7 节）；所有权五态 | 保管等待的一方 | 送达时、唤醒时 |
| 一群会话 | 协作图谱上一步接一步，每一步三个决定：下一个是谁、给他什么、停不停 | 协作轨迹 | 中心，即我们 | 每一步做决定时 |

- **外层的一步，展开就是里一层的一整圈**：一群会话里的一步，是某个会话的一轮；一轮里的一步，是一次模型或工具调用。这就是《核心抽象》3.5 的嵌套、《核心概念与理论地图》的递归闭合（团队即个体，子系统即渠道）。
- **能力层和协作层是这根轴的两段**：一个会话及以内归能力层，两个会话之间及以上归协作层。《核心抽象》第 1 节的判据正好对上：换个产品会过期的是能力层，换个议题会过期的是协作层。
- 同一个词出现在不同尺度上是正常的。“等”在一轮里是等回应（等审批、等回答），在一个会话里是让出后等后台任务，在两个会话之间是等对方交回（等子智能体）。说的时候带上尺度，就不会混。

### 理论极限：上限由那一级决定，做不到就搬到上一级

- **上限 = 那一级循环开放的时机 × 我们拿到的、通向那一级宿主的适配路线。** 一个产品“做不到”，要么它的循环在那个时机不看外面（谁也做不到），要么看但没给外面适配路线（换个位置可能就能做到，比如 Codex 的命令行不能插话，app-server 能）。
- **尺度越小，越依赖各产品开放**：一步、一轮的时机在它们的循环里。**尺度越大，越由我们自己决定**：一群会话这一级，宿主始终是我们，上限就是我们实现到哪。
- **补齐，就是把这件事搬到上一级、我们当宿主的那一级去做。** 轮内插话做不到，就排到下一轮（一个会话这一级），再不行就写进收件箱文件（信息层）；原生分叉做不到，就带着摘要新建会话（两个会话之间）；一轮中途的审批拿不到，就在新建时定好守卫和权限作用域；各产品不保管唤醒，就由我们保管等待、到点恢复会话。代价是粒度变粗：时效变慢、身份变了、记忆只剩摘要。补齐必须写明搬到了哪一级。
- **两条性质边界**，不是哪一个产品的缺陷：系统提示词新建后改不了；既不经事件流也不落盘的东西，外部看不到。
- 每个单元的上限和补齐办法：设计目录《能力单元与协作拓扑_完整性检查_20261018》4.2。

### 位置：能力从本体到使用者的通路

```
                         智能体本体（模型 + 循环 + 会话）
     ┌─────────┬─────────┬──────────┴──┬──────────┬────────────┐
  桌面端界面    命令行    常驻协议服务    ACP 桥      专用 RPC     本地会话文件与库     原生面（各产品暴露的）
  （人在用）              app-server、serve         Connect-RPC、agentapi
     │          │          │             │           │            │
  OpenCLI、    命令行     app-server     acpx（命令行   RPC 驱动    只读旁路            适配路线（我们去接的）
  直连 CDP     驱动       驱动          或嵌入运行时）
     └──────────┴──────────┴──────┬──────┴───────────┴────────────┘
             我们的后端：统一成一套接口；哪一级做不到，就在这里当宿主补齐
                    ┌─────────────┴──────────────┐
               网页（人用）                命令行网关（智能体用）
  反方向：智能体经钩子、装进它里面的工具和技能、命令行网关来找我们（上报、请求、让出、派活）
```

- **原生面按交互方式分**，就是《适配器模块设计》2.2 的七类接口面：会话文件读取、一次性运行、流式运行、服务协议、队列或桌面投递、钩子、桥接打包。“各产品的入口”一节的“九类入口”是这些面在各产品的具体例子，外加我们自己的 acpx 路线。它们是同一根轴上粗细不同的刻度。
- **桌面端界面也是一个原生面**，只是默认使用者是人。挂在它上面的路线是 OpenCLI 和直连 CDP，所以“读写桌面端自己记的置顶、分组、已读”“在桌面端窗口里发话、人在那边看得见”只能走这条路。它的截图和界面结构，也是在桌面端界面这个位置上取证的手段。
- **宿主是持有某一级循环的那一方**：各产品的桌面端、app-server、命令行进程是原生宿主，`hosts/` 档案卡写的就是它们；我们的后端经 ACP 拉起智能体时，接过了那个会话的宿主；在一群会话这一级，宿主始终是我们。
- **一个具体会话也落在这根轴上的一个点**：同一个产品，人在桌面端开的、命令行开的、app-server 里跑的、父会话派出的子智能体、我们经 ACP 拉起的，是不同的入口，能做的事不一样；再加上此刻谁持有它（所有权）。所以“这个会话现在能做什么”由“产品 × 入口 × 所有权”这个点决定，不由“产品”决定；后端给网页和智能体的能力，应当按会话所在的点给，而不是按产品给。读和控也必须是同一个会话身份，否则同一个会话会在列表里分成两条。
- **两个使用者对应两个目标**：网页对应“像原生应用一样简单”，命令行网关对应“暴露给智能体调用、实现多智能体协作”（用户 10-18）。

### 每一级由谁当宿主，我们就在那一级做什么

把尺度和位置交叉起来，系统的样子就出来了：一级的循环在谁手里，谁就决定这一级能做到哪；各产品不当宿主的那几级，只能由我们当。

| 尺度 | 谁当宿主，所以我们的后端做什么 | 人在网页上该能 | 智能体经命令行网关该能 |
|---|---|---|---|
| 一轮之内 | 各产品。我们接通：各产品开放了的接进来；没开放的换一条适配路线（app-server、Connect-RPC、OpenCLI、直连 CDP），再不行搬到下一轮 | 看每一步在做什么，停，插话，答审批和提问 | 发一轮、看进度、取结果、打断 |
| 一个会话 | 各产品；经 ACP 由我们拉起时是我们。我们管会话的一生：从新建到关闭都能经我们，人开的会话也能接管 | 选项目、选产品和模型新建，切换、改名、换模型，看产出 | 指定会话发话，接管人开的会话 |
| 两个会话之间 | 同一个产品内部是它自己（子智能体）；跨产品没有哪一个产品持有，只能是我们。我们当中间人：保管等待，负责送达、回执、唤醒、交回，记清会话归谁 | 看谁派给谁、在等谁、交回了没有 | 派活、送达、让出、上报 |
| 一群会话 | 始终是我们。我们当中心：每一步决定下一个是谁、给他什么、停不停 | 待处理、项目、协作图 | 看任务板、领活、交回 |
| 底座 | 能力渠道归我们，运行环境（终端、浏览器）在各产品和本机。我们供给：替每次调用选渠道，把终端、浏览器、产出物接出来 | 选模型，看用量 | 选渠道 |

- **尺度越小，越是接通和找适配路线**：做不做得到看各产品开放到哪，缺口多半要派研究。**尺度越大，越只能我们自己当宿主**：各产品不会给，缺口都是自己做。
- **用户的两个目标落在这张表上**：“像原生应用一样简单”主要是一轮之内、一个会话这两行的网页那一列；“暴露给智能体调用、实现多智能体协作”主要是两个会话之间、一群会话这两行的命令行网关那一列。
- 拿这张表对着现在的后端、网页、命令行网关看，空着的就是还缺的；逐格的数在 `probe/CAPABILITY_MAP.md` 开头（外层，生成）。

### 能力单元在这个空间里的位置

每个能力单元由两样确定：发生在哪个尺度，做的是哪类事（看、说、控、管、等）。它在通路上每个位置都有自己的样子：

| 单元 | 桌面端界面 | 原生接口 | 我们的后端 | 我们的网页 |
|---|---|---|---|---|
| 打断（一轮） | 停止按钮 | ACP `session/cancel`；Antigravity Connect-RPC `CancelCascadeInvocation` | `/api/gateway/cancel` | “停”按钮 |
| 读一轮全过程（一轮） | 每一步的折叠卡片 | 会话文件、事件流 | `/api/sessions/<编号>` | 思考、工具卡、红绿对比 |
| 置顶（一个会话） | 右键置顶 | Codex 本地库 `threads.is_pinned`；OpenCLI `codex pin` | 还没接 | 只记在手机本地 |

- **登记表里的人机交互单元，就是能力单元在人用的两个位置（桌面端界面、我们的网页）上的样子。** 从“网页接近桌面端”反推接口，就是从这两个位置沿着通路往回找它背后的单元。人机交互单元有三种：背后有能力单元的（停、工具卡、置顶）；只是使用者自己的性质（外观、排版、页面反馈）；只有在一群会话这一级才有的（跨产品的待处理流、协作图），桌面端没有，是我们独有的体验。
- **按尺度排**：
  - 一轮之内：看过程、插话、下一轮、打断、答复审批、回答提问；
  - 一个会话：新建、恢复、接管原生会话、分叉、回退、压缩、切模型、切模式、关闭、命名与元数据、新建时的配置、待命与唤醒；
  - 两个会话之间：派活、送达、唤醒、交接、互相发消息、所有权；
  - 一群会话：任务板、目标与预算、循环熔断、待处理、协作图谱与轨迹；
  - 底座：能力渠道（模型、额度、并发、按调用选渠道）和运行环境（终端、浏览器、产出物、本机探测）。

### 怎样承载海量单元：每个单元在每个位置只登记一处

总目标要每一层都能承载海量能力单元，并且清晰可见、可维护、可被调用、可被编排。做到这一点只有一个办法：**一个单元在通路的每个位置上只登记一处，其余的东西都由登记推出来**，而不是每加一个单元就去各处手写一遍。

| 位置 | 登记什么 | 登记在哪 | 由它推出来的 |
|---|---|---|---|
| 理论 | 单元的定义、判定标准、所在尺度、理论上限 | 设计目录《能力单元登记表》《完整性检查》4.2 → `hub/data/capability-units.json` | 所有矩阵的行；探针要测什么 |
| 原生面、适配路线 | 某个产品的某个入口能不能做、怎么做 | 适配路线自己声明它覆盖哪些单元；做没做到以黑板实测为准（`probe/blackboard.jsonl`） | 原生接口、适配路线两个矩阵；该派什么研究 |
| 我们的后端 | 这个单元经哪个接口调用，补齐搬到了哪一级 | 写在实现旁边的声明，汇总成能力注册表（`/api/capabilities`），不靠手标 | 命令行网关能调什么；网页能画什么；后端实测怎么测 |
| 网页、命令行网关 | 这个单元给人、给智能体长什么样 | 一处呈现规则（一类单元一种控件），按会话所在的“产品 × 入口 × 所有权”从注册表取可用动作 | 每个会话上出现哪些按钮、哪些命令 |
| 一群会话 | 单元能被编排：谁在什么时候调用哪个单元 | 协作定义（任务书、角色、协作图谱）引用单元的名字 | 协作轨迹；编排 |

- **拓展的负担应当是**：新接一个产品，写它的适配路线、声明覆盖哪些单元、跑一遍按登记表生成的探针；新做一个功能，登记一个单元、在后端写一处实现和声明。注册表、网页控件、命令行网关、测试、矩阵都跟着变，不用逐处手改。
- **判断架构有没有做对**：拿“加一个单元、加一个产品要改几处”来量。哪一处必须手改又不是登记处，哪一处就是要拆的地方。另一把尺子是下一节“管线”：它必须短到一眼看完，就知道怎么调用每个产品每一层的能力、怎么维护、出了 bug 怎么查。哪一步要写长才说得清，那一步的管线就还不够干净。
- 落到数据上，就是下面“管线”里的四张表：产品、动作、单元 → 动作、现状。
- 编排是最上面一层的调用：协作图谱里的每一步，都是在某个会话上调用某个单元。单元在下面几层登记清楚了，编排才只需要写名字。

### 七个矩阵是这个空间的切面

在通路的某个位置上切一刀，看所有单元、所有产品，就是一个矩阵。

| 矩阵 | 在哪个位置切 | 覆盖率怎么算 |
|---|---|---|
| 理论能力 | 智能体本体，按尺度推上限 | 是其余各矩阵的分母 |
| 桌面端人机交互 | 桌面端界面（依据多为截图和代码分析） | 是网页体验的分母之一 |
| 原生接口 | 每个原生面 | 除以理论 |
| 不同适配路线 | 每条路线 | 除以它挂的那个原生面 |
| 适配器 | 我们的后端 | 除以各原生面合计 |
| 我们的 web 体验 | 网页 | 除以桌面端界面，加上我们独有的那部分 |
| 实际能力 | 所有位置里实测最好的 | 除以理论 |

由脚本生成：`probe/CAPABILITY_MAP.md`（`probe/scripts/build_coverage.js`），数字只看它；它开头按这些轴把现在的差摆了出来（外层）。**相邻两个位置之间的差，就是要做的事**：理论和原生面之间的差，派研究（找入口，或认定补齐到哪一级）；原生面和路线之间的差，选路线、写驱动；路线和后端之间的差，接进来；后端和网页之间的差，照桌面端做。

### 文档挂在这个空间的哪里

- **语言本身**：本节，加上登记表（单元和五档）、术语表、《核心抽象》、《完整性检查》里的定义和定律。别处可以复写，可以拓展，不能冲突。
- **其余文档都是用这门语言写成、落在某些坐标上的话**：
  - 各产品的档案（`hosts/`）落在“产品 × 原生面”；
  - 路线的设计和研究（《适配器模块设计》、P3 任务定义、OpenCLI 研究）落在“路线”；
  - 单元的研究（唤醒、分叉、子智能体、HELLO_CHECK）落在“单元 × 尺度”；
  - 黑板的每一行是“产品 × 位置 × 单元”上的一句话，带依据；
  - 生成的矩阵是切面，它开头的“现在还缺什么”是切面上的差；
  - 任务书落在某个差上；
  - 评估、台账是过去某个时刻说过的话。
- 《核心设计总览》第 8 节的 X、Y、Z 三层也在这里：X 是这门语言；Y 是某个任务落在某些坐标上的定义；Z 是位置轴上的适配路线。

## 管线：怎么调用、怎么维护、出了 bug 怎么查

整条管线只有四张表。每张表是一份数据，代码照它运行，一条命令能把它打印出来并和代码核对：

```
node hub/tools/agent_gateway.js tables
```

| 表 | 一行是什么 | 文件 | 照它运行的代码 |
|---|---|---|---|
| 产品 | 一个智能体产品：走哪条适配路线、会话记录在哪、模型、环境变量；每条路线上每个动作实际执行的命令 | `hub/data/products.json` | 后端 `gateway.ts` 的 `CHANNEL_PROFILES`、命令行网关 `agent_gateway.js`，两处都从它取 |
| 动作 | 后端提供的一个操作：方法、路径、做什么、命令行网关的哪个子命令调它 | `hub/data/actions.json` | `server.ts` 的路由；请求字段由核对从路由代码里抽 |
| 单元 → 动作 | 一个能力单元由哪个动作实现、对哪些产品、做到什么程度（实测通过、部分、补齐到哪一级、实现了未测） | `hub/data/integration-map.json`（单元本身在 `hub/data/capability-units.json`，来自《能力单元登记表》） | 网页和后端的能力开关都由它推出 |
| 现状 | 每一层的理论极限、我们的目标、现状、依据记在哪 | 生成：`probe/CAPABILITY_MAP.md` 开头 | 依据是黑板 `probe/blackboard.jsonl`，每行带命令和输出 |

- **调用**：单元 → 动作 → 产品的路线上的命令。网页的按钮和命令行网关的子命令是同一个动作的两种外观。运行中的系统也给同样的东西：`GET http://127.0.0.1:8899/api/capabilities` 返回四张表的汇总。
- **维护**：加一个单元，在“单元 → 动作”加一行；接一个产品，在产品表加一行，路线没有的话在同一个文件的 routes 里加；加一个动作，在路由和动作表各加一行；加一个网页控件，在“单元 → 动作”那个单元的 frontend 条目里写 `ui`（放在哪：会话栏 session-bar 或会话的“更多” session-more，顺序、名字，以及页面里的处理函数或要调的操作），“更多”里的会话操作只要这一行数据，页面照 `/api/capabilities` 的 controls 自己生成。然后跑 `tables` 核对，跑 `node probe/scripts/build_coverage.js` 重出现状。核对对不上的地方会逐条列出来。
- **出了 bug**：沿网页 → 后端接口 → 运行记录（`~/.agent-hub/runs.jsonl`、`~/.agent-hub/hub-8899.log`）→ 产品表里那条命令手动跑一遍 → 产品表里写的会话记录位置，逐层对。断在哪层修哪层，修完在黑板补一行实测，再重出现状。改后端先 `node -e "import('./trace/apps/cli/src/server.ts')"` 能加载，再按 8899 端口停进程，用命令行网关任一子命令让它自动拉起。
- **回归**：`node hub/tools/agent_gateway.js verify [--product zcode,hermes] [--unit open,cancel,task-board]` 照四张表逐产品、逐单元真跑一遍，每格写一行黑板。另有五个专项：`probe/scripts/test_taskboard.mjs`（一群会话的判定，不调智能体，几秒）、`probe_acp_approval.js`（常驻 ACP 的轮内审批）、`probe_session_control.js`（切模式、压缩、分叉、推理力度）、`probe_ask_user.js`（智能体轮内向人提问、人答回同一轮）、`probe_display.mjs`（读取显示：每家抽真实会话，网页用的那份数据对着原始记录逐条核对工具调用、结果、思考字数、压缩、“非本人的话”，`--write` 写黑板；改了哪家的解析器就跑它，并把那家解析器的版本号加一，否则旧缓存不会重读）。摸一家产品自己有哪些能力（含操作电脑、浏览器这类高阶能力和各家优势）：按 `probe/SOP_对话探查生态功能.md` 走，先问、再演示、别人复跑通过才写黑板。智能体要回看自己会话过去的对话：`agent_gateway.js recall --agent X --session <名> [--grep 词] [--last 5]`（单元 recall-history，派活单的协作说明里也写了）。8899 上有别人的轮在跑、不能重启时，新代码在副本上测：`HUB_BACKGROUND=0 node trace/apps/cli/src/main.ts serve --port 18904`，这份只应答请求，不巡检、不推进目标、不整理派活单，专项脚本加 `--base http://127.0.0.1:18904`；副本再加 `HUB_DATA_DIR=<临时目录>`，它开的目标和任务就不会落进 8899 读的目录。手动重启 8899 要带局域网参数：`node trace/apps/cli/src/main.ts serve --port 8899 --lan $(cat ~/.agent-hub/lan-host)`，漏了它手机打不开（10-19 踩过）。

后端各块在哪（一块一个文件，同时改不同的块不冲突）。`gateway.ts` 只留类本身：字段、发话和停止、一轮的收尾、状态与设置；其余每块是 `gateway/` 下一个文件，以 `this` 是后端的函数写成，挂回类上，调用方式不变：

## 基础概念

项目自己的术语以《术语表》《核心抽象》为准，这里只做入门解释。《术语表》有一条硬规矩：“层”“适配器”“会话”“恢复”这类多义词不能裸用，要说清是哪一种。

**智能体与会话**

| 词 | 意思 |
|---|---|
| 智能体 | 能用工具、自己多步干活的模型程序，例如 Codex、Claude Code。本文说“智能体产品”（简称“产品”），指同一套循环和会话存储、可以有几个入口的一个产品，见“立体认知”的“用词” |
| 会话 | 一段有编号、能接着做的工作记录（《核心抽象》§2.1）。进程还在叫“热”，只剩磁盘记录叫“冷”，热和冷只是快慢差别 |
| 原生会话 | 各产品自己创建、自己认的会话，格式不由我们定 |
| 轮 | 从送进一份输入，到智能体交出这一份的结果为止。一轮里有很多步：调模型、调工具、请求审批 |
| 三个状态 | 执行中（工作中，或在等审批的回应）；待命（可以接新输入，记着“怎么进来的”和“在等什么”）；关闭 |
| 宿主 | 把智能体跑起来的程序，替它管进程、权限、等待。可以是桌面应用、守护进程，也可以是我们的后端 |
| 子智能体 | 一个会话在自己内部派生出的会话，干完一块活把结果交回 |
| 守护进程 | 一直开着、随时接请求的后台进程 |
| 一次性命令行 | 每次调用拉起一个新进程，跑完一轮就退出，下次靠会话编号恢复会话 |
| 工作目录 | 智能体干活的项目目录（cwd） |

**协议与接入**

| 词 | 意思 |
|---|---|
| ACP | Agent Client Protocol，宿主驱动智能体的标准协议，在标准输入输出上走 JSON-RPC。常用方法：`session/new` 新建会话、`session/load` 加载会话、`session/prompt` 送一轮输入、`session/cancel` 打断、`session/request_permission` 智能体请求审批。ACP 没有轮内插话 |
| ACP 桥 | 把某个产品包成 ACP 的程序，例如 `codex-acp`、`claude-agent-acp` |
| acpx | 统一调用各产品 ACP 桥的命令行客户端（本机 0.19.5），会话记在 `~/.acpx/sessions/`。它也能当库嵌进我们的程序（`acpx/runtime`） |
| app-server | Codex 自己的常驻协议服务（JSON-RPC），能力比它的 ACP 桥全 |
| MCP | 给智能体加工具的协议。ACP 管“谁来驱动智能体”，MCP 管“智能体能调哪些工具” |
| CDP | Chrome 调试协议。桌面应用开了调试端口时，外部能像操作网页一样操作它；opencli 就用它 |
| 钩子 | 智能体在约定时机（会话开始、提交输入、工具调用前后、收尾）自动执行的脚本 |
| stopReason | ACP 里一轮结束的原因：`end_turn` 正常结束，`cancelled` 被取消，`refusal` 模型拒答，`max_tokens` 输出到上限 |
| agentapi、Connect-RPC | Antigravity 的两个本地控制接口：`language_server.exe agentapi` 是命令行形式，Connect-RPC 是它在本机端口上开的 HTTP 接口（332 个方法） |
| tap 协议、文件收件箱 | 把要送给智能体的话写进约定的文件，智能体在合适的时候自己去读；tap 是本项目早先定的这种文件约定 |
| 让出 | 智能体自己结束这一轮，并写明在等什么（等审批、等别人、等后台任务），会话进入待命 |
| 审批 | 智能体做有风险的事（写文件、跑命令）前向宿主请求许可。权限模式决定没人答时默认怎么办；我们的默认是只读 |

**渠道与账号**（见“能力渠道”展开）

| 词 | 意思 |
|---|---|
| 能力渠道 | 让智能体跑得起来、用得上的那一层：运行载体（模型、执行器、额度与账号）和调用能力（工具、技能、检索、其他智能体、执行环境）。运行载体出事，跑在上面的智能体一起停；调用能力出事，要排队 |
| 供应商 | 一套“请求发往哪个地址、用什么凭证、默认什么模型”的配置。同一个产品智能体可以登记多个供应商 |
| 登录态 | 用这个产品自己的账号登录（多是 OAuth），额度算在账号或订阅上。例：ZCode 的智谱 Coding Plan、Claude 桌面的官方登录、Antigravity 的 Google 账号 |
| 中转站 | 第三方转发服务：给一个接口地址和一把 key，替你转到模型厂商。例：yinzi（api.yinziapi.top）、2chat |
| key | 调用接口用的密钥 |
| 额度 | 账号或 key 还能用多少；用完了会报错（例：403 余额不足、429 限流） |

## 协作拓扑：协作由什么拼成

出处：《基础能力推演_20260929》（用户 09-29 确认）、《核心抽象》§3～§4、《核心设计总览》§1～§7、《可视化架构》§3.3～§3.4、《协作定义方式》§2～§4、sota《协作交接分析》§〇～§四。

**1. 最小单元是“问答”。** 中心想让一个智能体说一句话，要做三件事：把输入送进去；等这一轮结束；把这一轮的输出取出来。怎么送进去，看对方的状态：

| 对方的状态 | 用哪个能力单元 |
|---|---|
| 正在运行，而且能接收插话 | 插话 |
| 空闲，有旧会话，需要它记得前面的内容 | 恢复会话 |
| 没有会话，或者希望它不带旧记忆（例如独立评审） | 新建会话 |

所有协作都由问答拼成。两个智能体讨论，就是交替的问答：A 的会话记得自己说过什么，只需把 B 的新话给它。“这一轮做完了”和“这一轮说了什么”，只有中心自己启动的运行才能准确把握，人开的会话只能靠读记录推断，所以讨论要用中心启动的会话。

**2. 每一步三个决定，答案来源可以配置。** 下一个是谁、给他什么、停不停。答案可以来自事先写好的规则（工作流驱动）、某个智能体的输出（智能体驱动），或者两者同时：规则划定范围，智能体在范围内提要求，中心照办，超出范围的交给人。三种方式用的是同一套能力单元，区别只在答案从哪来。三个决定分别落在三个核心层上：下一个是谁落在智能体和它的渠道上，给他什么落在信息上，停不停落在任务的验收、闸门、返工上限上。

**3. 智能体把决定告诉中心的两条路。**

| 路 | 怎么做 | 需要什么 | 特点 |
|---|---|---|---|
| 甲：写在输出里 | 约定格式，比如回复末尾写“下一位：B”“结束：理由” | 只需要能读到输出 | 所有产品都能用；要等这一轮结束才生效 |
| 乙：调用中心提供的工具 | 一轮中直接调“找 B 问一下”“结束讨论” | 产品支持 MCP | 即时，可以在一轮中间发生 |

一轮中间想问另一个智能体：A 调工具“问 B”，中心对 B 做一次问答，把回答当工具结果还给 A。工具调用等不了那么久时，中心先回“已转交 B”，A 让出；B 答完，中心再恢复 A 的会话。这两种都用现有的能力单元拼出来。

**4. 五种形状 × 三种决定来源，拼出常见的协作方式。**

| 形状 | 意思 |
|---|---|
| 接力 | A 的输出成为 B 的输入 |
| 分发 | 同一件事同时问几个人 |
| 汇总 | 几个人的输出合起来，交给一个人 |
| 往返 | A 和 B 来回好几次 |
| 共享 | 中心保存一份共同材料，每次问答都带上它 |

| 常见说法 | 拼法 |
|---|---|
| 实现后评审、修改 | 接力 + 往返，规则决定 |
| 两个智能体讨论 | 往返，规则或主持人决定 |
| 主管派活 | 分发 + 汇总，主管智能体决定 |
| 交接（handoff） | 接力，当前智能体决定下一个是谁 |
| 群聊 | 多人往返，规则或主持人决定下一位 |
| 辩论 + 裁判 | 往返 + 汇总，规则决定 |
| 黑板 | 共享 + 按内容决定下一位 |
| 任务池 | 共享任务清单，智能体自己认领 |

两种执行方式：问答（短、同步，靠恢复会话记住前文，适合讨论）和任务（长、异步，靠认领，交付文件，适合调研）。一轮隔几小时用任务；几分钟一轮、要有发言顺序用问答加主持人；几秒一轮、来回很多次的，整段交给一个智能体让它内部组队。个体可以嵌套：一个个体内部可以是一个团队，外层只看它交出的东西。

**5. 图上的四类连线**（协作图谱怎样画）：任务线（派发、交付、打回、上报）、信息线（读谁的产出、信息送达）、监督线（谁看着谁）、渠道线（使用、提供、维护）。每条线对照三种状态：编排里有、也确实发生了；只有定义、没发生；只有事实、编排里没有（要醒目标出）。图上的每种线，在轨迹里都要有对应的事实：任务线对应交接，监督线对应观察和介入，信息线对应送达和读写，渠道线对应调用。

**6. 交接：协作在现实里出事的地方**（sota 第 1 轮实测）。八种交接：

| 交接 | 是什么 |
|---|---|
| 流水线交接 | 上游的产物交给下游接着做 |
| 服务请求 | 交给服务角色去办，办完送回 |
| 验收与退回 | 交给独立的人检查，不合格返工 |
| 接续 | 同一角色换实例：崩溃、超时或上下文满了，新实例接着做 |
| 拉起 | 派发者启动一个执行进程：提示词、必读文件、沙箱、模型渠道 |
| 控制权与审批 | 谁说了算，从一方转到另一方 |
| 产品与黑板对账 | 智能体产品自己的运行状态和我们的台账要对上 |
| 规则传播 | 规则改了，正在跑的和以后的实例怎么知道 |

由交接组成的协作结构有七种，各有典型的坑：扇出扇入（兄弟之间重叠或漏分支，扇入时没人收）；生产与核查（口径漂移，同一模型家族一起漏掉同类错误）；服务队列（服务方不在，队列只进不出）；同一文件接力（同时写会覆盖，只能串行）；中心与外围（中心是单点，外围绕过中心）；监看（监看者顺手做了决策者的事）；跨产品互修（修的人不在角色表里）。

第 1 轮得出的判断：
- “认领”之前还有“拉起”。智能体只有被启动才存在，拉起要像需求一样有格式、有账本，启动提示词只指向需求文件，不重抄路径。
- 角色活得长，实例活得短。一个角色跨几个阶段的职责要拆成几件需求，用依赖串起来，连续性靠记忆文件。
- 两套状态机（智能体产品自己的运行状态、我们的任务状态）要有映射表，每个状态只有一个写者；依赖只认“完成”，不认“等待验收”。
- 写了规则、却没有机制兑现的，基本都没兑现；格式类检查交给脚本。
- 交接包由四样组成：需求文件、角色任务书、记忆文件、上游产物的路径；启动提示词只是指向它们的指针。每份产物带“身份三件套”（角色、产出它的智能体产品或会话、运行编号）和系统时间。
- 出错后的回路：作者自查 → 脚本体检 → 范围验收 → 事实核查 → 闸门 → 下游使用时发现；第二次退回就升级，由总调度裁决；下游不改上游文件，写升级单。

**7. 写协作定义时的取舍。** 三个旋钮：个体和渠道写得多死；三个决定交给规则还是交给智能体或人；任务之间共享多少信息、依赖多紧（耦合）。规格总量大致不变：钉死个体和渠道，流程就可以空着；钉死流程，个体就可以很薄。没钉死的部分要在运行时由模型解出来，解多少烧多少 token。粗粒度优先：人在粗粒度上指挥，模型在粗粒度上最能发挥，方法论也写在粗粒度上；细的流程靠监控和测评从粗的降下来，只往细降，情况不再重复出现就停止降。

**8. 推到边界后要补的三处说法**（《能力单元与协作拓扑_完整性检查_20261018》§2.3）：决定点由什么触发（一轮结束、事件、定时、人的回复，也就是唤醒，它连着拓扑和能力单元）；“给他什么”= 信息 ＋ 授权与资源（工具、权限、预算、工作目录、模型渠道）；角色和实例的对应（谁是某个角色现在的实例）要看得见。另有一条协作层机制要补：拉起契约与实例台账（派活时由中心生成只含指针的启动包，并把任务、运行、角色、会话、目录、时间记进台账），方向 3 和方向 6 都推出了它。五种形状作为拼法的基，拿工作流控制模式核对过，是全的。

**9. 用户的原则**（总览原话 25）：“先找通用抽象，再对各家做适配”。09-29 推演的结论是：协作真正需要补进底座的只有三件事——问答是一个可靠的组合操作（按对方状态自动选插话、恢复会话或新建会话）；三个决定的答案来源可以配置并写明照办范围；智能体向中心提要求的甲乙两条路。其余（讨论区、给下一位看哪些话、停止条件、运行中增减成员）都在这三件事之上用规则和模板实现。

## 链路：网页、后端、适配器、各智能体产品

用户的说法：“我们总共就三层，前端，后端和适配器，各家agent”。

```
人
 │
网页         手机督工台 /m/（m/index.html，10-18 负责人重写，照能力注册表画）；/console/ 与首页对话抽屉（旧）
 │  HTTP（/api/capabilities、/api/sessions?slim=1、/api/sessions/<id>、/api/search、/api/gateway/*）
后端         统一服务 trace/apps/cli/src/server.ts + gateway.ts（端口 :8899）
 │           命令行网关 hub/tools/agent_gateway.js：智能体用的协作接口；服务不在时自动拉起服务，--standalone 才自己直接调
适配器       acpx（每次拉起一个子进程）→ 各产品的 ACP 桥
 │           Antigravity 没有公开的 ACP 桥，后端直接调它的 agentapi 和 Connect-RPC
各智能体产品    各产品自己的命令行、守护进程、本地端口、会话文件
 │
模型（经能力渠道：登录态、中转站、官方接口）
```

- **适配器这一段的控制代码在哪**：没有单独的模块，写在后端里。`gateway.ts` 的 `CHANNEL_PROFILES` 登记每个产品怎么调 acpx（命令、模型、环境变量），`startRunInternal()` 拉起 acpx 子进程并解析它的输出，Antigravity 的 agentapi 调用也在同一个文件里；`agent_gateway.js` 里还留着旧的直连路径，只在加 `--standalone` 或服务拉不起来时才走。把这一段抽成独立的驱动，就是 P3（评估文档第四节的分步计划：P3 是把 ACP 系六个产品改走嵌入的 acpx 运行时，P3b 是 Codex、Claude 的原生驱动，P5 是能力渠道接入）。
- **“跑一轮”只有一份实现（10-18）**：在后端 `gateway.ts`。命令行网关是薄客户端：服务不在时它自己拉起服务（读 `~/.agent-hub/lan-host` 带上局域网参数），超时报“还在跑”（退出码 3）而不是失败，`read`/`wait` 取结果，发出后断线不重发；运行记录写 `~/.agent-hub/runs.jsonl`，重启后仍可读。之前两条路径各写一份，行为分叉，每个修复要改两遍，这是根因。
- **能力注册表是网页和智能体的共同依据（10-18）**：`GET /api/capabilities` 把 `hub/data/capability-units.json`（登记表生成）和 `hub/data/integration-map.json`（负责人登记的实现路径，含机读的 `api` 字段）合在一起：每个产品每个单元，后端和网页做到哪、调哪个接口。页面照它决定显示哪些按钮，不再自己猜。
- **拉起 acpx 不经 cmd.exe（10-18）**：后端用 node 直接跑 `acpx/dist/cli.js`，多行参数（比如追加的系统提示词）原样到达；只有找不到这个文件时才退回 `cmd.exe /c acpx …`，那条路会在换行处截断参数。
- **权限默认全放行（用户 10-18：“我们所有智能体都是全权限运行”）**：后端、网页接口（`parsePermissions`）、命令行三处默认都是 all，只读要明说。之前网页发话不带权限字段时被定成只读。
- **不写模型就沿用会话自己的模型（10-18）**：顺序是本次指定 → 这次运行里选过的 → 会话记录里的当前模型 → 这个产品的默认。之前服务重启后会悄悄退回默认模型，命令行也会自己填默认模型。
- **只读旁路**：`trace/packages/adapters/src/<产品>/` 加 `store.ts`，被动读各产品落在磁盘上的会话记录。读和控用的是两套会话身份，这是“点开原生会话发消息，却新建了一个空会话”的根源。10-18 部分解决：对一个产品自己写的会话发话时，后端给 `acpx sessions ensure` 带上 `--resume-session <原编号>`，接上原会话而不是另开（WorkBuddy 实测答出原会话里的暗号；Codex 能找到原会话，但已归档的会被拒）。没解决的：接上之后列表里仍有原生和 acpx 两条记录；分叉出来的会话编号会变（见“状态判据” Claude 一行）。
- **控制链是可选的增强，不是前提**（评估文档第十节第 1 条）。项目的系统原则是：智能体不依赖中枢，中枢停了照常干活，文件是唯一真源。所以不能让“没有网关就不能干活”成立；接入要分档（零集成、预设注册、钩子、深度集成），嵌入运行时属于最高一档。
- **使用逻辑是工作台。** 每个会话都可以选项目目录。新建会话默认放进一个新目录：`HUB_WORKSPACE_ROOT`，默认 `C:\Users\COLORFIRE\hub-workspaces\<产品>-<会话名>-<时间>`。网页目录下拉的第一项是“🆕 新目录（默认）”（数据里记作 `__new__`）；选了真实目录就原样使用；同一个会话恢复时沿用第一次的目录（用户 10-18 纠正：“默认新会话应该是新目录。然后可以选择目录”）。
- **环境变量要清理。** 在 Claude 宿主里启动的进程会带上 `CLAUDECODE`、`CLAUDE_*`、`ANTHROPIC_*`；子进程里的 claude 拿着它们会报“未登录”或答非所问。后端拉起智能体前先去掉这些（`agentBaseEnv()`），Claude 再从 `~/.claude/settings.json` 的 `env` 里取 `ANTHROPIC_*` 供应商变量（`claudeProviderEnv()`）。代理变量不清理。这和 agent-hub 的 `runs.platform_env()`、《适配器模块设计》§9 是同一条规则。

## 各产品的入口

“入口”指同一个产品的不同接入方式。同一个产品的不同入口能力并不等价（用户 10-17：“codex原生对话（人打开的页面），以及subagent和app-server的不一定等价”），所以能力要按“产品 × 入口”记，不能按产品记。

**通用的九类入口：**

| 类 | 例子 | 谁在用 |
|---|---|---|
| 人开的交互会话 | 桌面应用、终端界面、IDE 插件 | 人平时用 |
| 子智能体 | Claude 的 Task/Agent、Codex 的 `spawn_agent`、Antigravity 的 `invoke_subagent` | 智能体自己派生 |
| 后台与守护进程 | `claude --bg`、`codebuddy --bg`、`codex app-server daemon`、`droid daemon`、`hermes gateway` | 长任务、共享服务 |
| 一次性命令行 | `codex exec`、`claude -p`、`opencode run`、`droid exec`、`gemini -p`、`codebuddy -p` | 脚本、测试 |
| 常驻协议服务 | `codex app-server`、`claude --input-format stream-json`、`opencode serve`、`zcode app-server --stdio`、Antigravity Connect-RPC | 程序深度控制 |
| ACP 桥 | `codex-acp`、`claude-agent-acp`、`zcode-acp-server`、`codebuddy --acp`、`opencode acp`、`gemini --acp`、Hermes `acp_adapter` | 编辑器、acpx |
| acpx 命名会话 | `acpx <产品> prompt -s <名字>` | 我们的后端现在走这条 |

| 钩子、MCP、文件收件箱 | tap 协议；Claude 收到 MCP 的 `notifications/claude/channel` 通知会被唤醒 | 往会话里送消息的降级手段 |

**接管别人开的会话**之前，先判断它现在归谁（《适配器模块设计》§5 所有权五态）：

| 状态 | 意思 | 我们能做什么 |
|---|---|---|
| owned_by_us | 我们启动并持有的进程或连接 | 投递、插话、打断、结束 |
| owned_by_app | 桌面应用或产品自己的守护进程持有 | 只能走这个产品的官方入口（队列或服务协议）；不能另起进程恢复它 |
| owned_by_terminal | 人正在终端或界面里用 | 只读，最多提示“在原应用继续” |
| released | 没有活动的写入者 | 可以恢复会话（先拿到中心内的锁） |
| unknown | 判断不了 | 按只读处理 |

推断出来的所有权只能用来禁止写入，不能用来放行。往人开的会话里投递时：人正在打字就先暂存；停在审批框时不盲推；恢复失败绝不悄悄变成新建会话（评估文档第十节第 4 条）。

**Codex 细说**（详见 `hosts/codex/` 四册：README、app-server、cli-commands、config-and-pitfalls）：

- Codex 的会话按入口分五种：人开的桌面或终端会话；会话里派生的子智能体（`spawn_agent`）；`codex exec` 一次性会话；`codex app-server` 里的线程（独立进程或共享守护进程）；经 `codex-acp` 桥建的会话（我们的后端经 acpx 建的就是这种）。它们都落在同一套 `~/.codex/sessions/` 记录里，但能做的事不一样。

- 人开的桌面或终端会话有单写者锁：被一个进程用过后约 7 分钟内别人写不进。外部给它送话要排队：`codex queue --thread <ID> --message <TEXT>`（本机 0.159.2 的帮助已核对；写成位置参数或 `-m` 都是错的，`-m` 是选模型）。
- `codex exec` 能恢复会话、能分叉、能换模型恢复，但一轮进行中送不进话。
- `codex app-server` 是唯一四项全通的入口：轮内插话、分叉、压缩上下文、中途切模型。常用方法：
  - `thread/start`：可带 `model`、`modelProvider`、`config`，只给这个会话换供应商或模型；
  - `turn/steer`：轮内插话，必须带 `expectedTurnId`；
  - `turn/interrupt` 打断、`thread/resume` 恢复会话、`thread/fork` 分叉；
  - `thread/inject_items` 只注入不触发推理；`thread/queue/*` 原生队列；`thread/goal/*` 目标与预算；`requestUserInput` 中途向人提问；
  - 审批会反向发给客户端（如 `item/commandExecution/requestApproval`）；
  - 状态看 `thread/status/changed` 的 activeFlags（`waitingOnApproval`、`waitingOnUserInput`）；`error.willRetry` 为真表示它在内部重连，不算失败；
  - `codex app-server generate-json-schema` 能导出当前版本的协议，用来查版本漂移。
- 钩子 11 类：Stop 能拦住收尾让它继续；SessionStart、UserPromptSubmit 能注入上下文。
- 子智能体的父子关系看 `thread/list` 的 `parentThreadId`；会话记录在 `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`，索引在 `~/.codex/state_5.sqlite`。
- 经 ACP 桥只能把话排到下一轮。

**其他几个产品要记的点：**

- Claude：子智能体记录在 `~/.claude/projects/<编码后的目录>/<会话编号>/subagents/agent-<id>.jsonl`。只给一次调用换供应商用 `--settings '{"env":{…}}'`；`settings.json` 的 env 优先于进程环境变量，单靠环境变量换不了。**红线（10-18）**：外部脚本读写或冷分叉复制 `~/.claude/projects/**/*.jsonl` 必须使用无 BOM UTF-8（严禁 PowerShell 5.1 `Set-Content -Encoding UTF8` 带入 `EF BB BF`，否则会导致桌面端连续性工具 `ClaudeDesktopContinuity` 解析首行 JSON 崩溃）；探针测试构造的合成 UUID 会话（如 `b0000000-...`）在取证完毕后必须原地删除，禁止遗留污染 `~/.claude/projects/`。
- WorkBuddy：经 acpx 要注入 `CODEBUDDY_CONFIG_DIR`、`WORKBUDDY_CONFIG_DIR`、`ACC_PRODUCT_CONFIG_V3` 三个变量，并用 `--model "custom-local:glm-5.3"` 走本地智谱 Coding Plan 额度。它有两套“套餐”：腾讯官方 Credits（二十多个内置模型，扣费倍率在 ACP 新建会话的 `configOptions` 里能读到，例如 glm-5.3 每次 0.79，hy3 和 deepseek-v4.1-flash 免费）；本地自定义供应商（`custom-local:glm-5.3`、`custom-local:glm-5.3-flash`，用智谱 Coding Plan，不扣 Credits）。原生命令行、ACP 桥、acpx 三条路都能按调用换模型；Credits 余额在无头模式下查不到，每轮消耗记在 `workbuddy.db`。
- ZCode：原生命令行不认模型参数；经 ACP 桥或 acpx 用 `供应商\模型` 的写法指定（例如 `builtin:bigmodel-coding-plan\GLM-5.3-Flash`、`new-provider-2\ark-code-latest`），同一个会话里能中途换模型、换套餐（智谱 Coding Plan 和火山方舟之间），本地库 `model_usage` 的供应商和模型字段逐轮对得上（10-18 实测并经负责人核对）。查额度：在会话里发 `/quota`，会当场显示智谱 Coding Plan 5 小时窗口用了多少、MCP 次数。派活推荐 Flash 档，要深推理再切满血档。详见 `probe/results/agy-pro-wb-zcode-plans-20261018.md`。
- Antigravity：四个端面（桌面应用、IDE、`agy` 终端界面、Python SDK）共用同一个 `language_server.exe`。外部调用 agentapi 要从这个进程的命令行取出 csrf token、找到它监听的第二个端口，再注入环境变量（token 不写进黑板和报告）。
- OpenCode：从程序里调用 `opencode run` 必须关闭标准输入，否则永久阻塞。

## 能力单元与适配器设计

**能力单元**的唯一登记处是设计目录《能力单元登记表_20261017》，本文不复制清单，只记读表时最容易混的几条：

- 三种形态：操作（中心对智能体做的，如新建会话、恢复会话、打断、插话）、动作（智能体向中心发出的：交付、请求、让出、上报）、状态（中心读得到的，如工作中还是待命、在等什么、额度还剩多少）。
- 往进行中的会话送话，按能做到的程度依次降级：轮内插话 ＞ 排到下一轮（原生队列，如 `thread/queue/*`、`codex queue`）＞ 夹在工具结果里捎带（任何支持 MCP 的宿主都能用）＞ 写进收件箱文件。能力标记要写明落在哪一级。登记表第 4 节第 1 条已于 10-18 改为四级。
- 打断只结束这一轮，会话还在；关闭会话连会话一起结束。恢复会话、接管原生会话、分叉是三件事：恢复的是自己的会话；接管要先接进别人开的会话的身份并处理锁；分叉是复制，原会话不动。
- 能力标记分五档：原生（这个产品自己的接口就支持）、经桥（经 ACP 桥或 acpx 支持）、补齐（这个产品不支持，由我们开发补上，要写明降到哪一级）、不支持、未测。只从黑板生成，不手写。

**能力单元是怎么一步步来的**（各处叫法都已落到登记表第 5 节，这里只记脉络）：
- 09-29《基础能力推演》：用户说的六个基本能力——读、看状态、发、新建、恢复、停；中心一侧维护项目、任务、上下文入口、状态、交接、成果。
- 10-08《核心抽象》§2.7：拆成必需五项（新建会话、恢复会话、观察、打断、关闭会话）、可选四项（插话、答复审批、分叉、压缩上下文）、守卫、智能体的四个动作（交付、请求、让出、上报）、待命的两个属性（原因、在等什么）；10-14 补了渠道级的查额度。
- 10-14《能力核对 v2.0》§2：六平台 × “5+4”的大矩阵，以及契约里的四档位图（只读观察、生命周期控制、往会话里送话、团队协同）。注意：这张矩阵几乎都是照各产品帮助文本写的声明，不是实测，里面也有错（例如 `codex queue` 写成了 `-m`）；它列的智能体四项主动动作是提问、汇报、记忆写入、调同伴，和《核心抽象》的四个动作口径不同。
- 10-17《能力单元登记表》：收拢以上全部，加上唤醒、渠道级、团队协同、人在环、宿主环境（本文叫运行环境）几类扩展，四十多项，是唯一登记处。
- sota《框架基本能力分析》的 47 项是“整个协作系统”要的能力（任务对象、租约、闸门、写权限、信号、文件记忆、决策链、独立验收、审批节点等），大多属于中枢和协作层，不是对单个智能体的操作；其中属于能力单元的几项（事件与唤醒、子智能体派生、实例接手、渠道锁、节奏闸、渠道切换）已收进登记表。

**认知还缺什么**（2026-10-18 盘点，补齐了就删掉对应的一条）。分两件事说：抽象本身全不全，靠推理检查，见《能力单元与协作拓扑_完整性检查_20261018》（六个方向都已做完，推出 22 个候选单元，已标“候选”登记进登记表，最要紧的是“挂接工具”）；各产品实际支持到什么程度，靠实验，缺口如下：
- 各产品支持度大多还没有可靠证据：109 格只由 flash 测试员记为“通”（正在由 ZCode、WorkBuddy 复测其中风险高的 33 格）；“子智能体”入口一条记录都没有（Antigravity 在查）；“人开着的会话”一个产品都没测（要用户配合）。
- 七个单元从没测过：按调用选渠道、渠道健康、交接，以及智能体的交付、请求、让出、上报。
- “记忆写入”（智能体把认知写进自己的记忆文件）在 v2.0 里算主动动作，登记表里没有对应单元，要不要登记待定。
- 《适配器模块设计》的十个耦合问题，还没有对任何一个产品逐条回答。
- 唤醒的五个子问题，除 Antigravity 外基本未测（见“唤醒”）。

**《适配器模块设计》的骨架**（做后端和适配器之前必读，这里只列要点）：

- 一个适配器由“能力清单 ＋ 若干接口面”组成。七类接口面：会话文件读取、一次性运行、流式运行、服务协议、队列或桌面投递、钩子、桥接打包（把中心的 MCP 工具装进智能体产品）。同一项能力常有好几条路可走。
- 选路规则：官方且已验证的优先；绝不悄悄换一种语义，例如“投递到原会话”失败后不能自动变成“新建会话”。
- 语义规则：同一个请求编号重复调用只执行一次（幂等）；结果不确定就返回 `uncertain` 交给中心去查，不自己重试有副作用的动作；做不到就返回 `unsupported` 并写明原因；只打断、只停自己启动的运行；不改用户的全局配置。
- 能力清单每项六种状态：verified（有证据通过）、declared（官方有、没测）、degraded（能用但有缺陷）、unsupported（确认做不到）、unknown（没研究）、broken（以前通、现在坏）。界面只对 verified 和 degraded 开放按钮。
- 回执分阶段：交给适配器、产品已接受、已开始、在会话里看到、已回复、不确定、失败。“已提交”不等于“已读到”，更不等于“已回复”。
- 比较各产品时最有区分度的是十个耦合问题，例如送达和唤醒能否分开、新建会话和首次运行能否分开、继续和分叉得到的是不是同一个身份（§12）。

## 唤醒（议题）

用户 2026-10-17：“其实你自己做成的这项能力，也是他们如果有最好的能力，分为agent的唤醒机制里，他们有没有这个也是值得研究的，你记录一下，并且思考和拓展相关内容”。来由：负责人把测试派到后台，靠“后台任务结束时的通知”被叫醒，不轮询；测试员 Antigravity 也在做同样的事。

**在我们抽象里的位置（不是新概念）**：《核心抽象》§2.5 进入待命有四种方式，其中“主动让出”要写明在等什么；该节最后一句是“协作层的触发规则，说到底是‘等的东西到了，就恢复会话’”。唤醒就是这个“恢复会话”由谁、凭什么触发，挂在“待命·在等什么”上。《适配器模块设计》§7 把它拆成“送达”和“唤醒”两件事：只送达不唤醒（写进收件箱，等它自己读）、送达加空闲时唤醒、运行中补充。

**唤醒从哪来**：
- 自己安排的：放到后台的命令结束（wake-bg）、约好的时间到了（wake-timer）；
- 外部送来的：中心、别的智能体、人发来的消息，子智能体交付，审批结果（wake-msg）；
- 环境变化：文件、端口、CI 状态（还没测，Claude Code 的 Monitor 类工具属于这一种）。

**最重要的认识：唤醒是宿主的能力。** 智能体只负责“让出并说明在等什么”，等待由宿主保管，到点或事情来了由宿主叫醒。证据：
- ZCode 的定时工具是向宿主发 `automation/*` 请求、请宿主代为定时；ACP 桥不提供这个端口，于是在无头模式下把这些工具禁用（黑板 71 行）。
- 叫醒负责人的是 Claude 桌面应用，应用关掉就没人叫醒（黑板 63 行）。
- Antigravity 的后台命令由常驻的 `language_server` 托管，结束后以系统消息送回（黑板 66 行）。

由此推出：谁当宿主，谁就得提供唤醒。我们的后端一旦当了宿主（经 ACP 拉起智能体），要么实现这些端口，要么明确告诉智能体“这里不能定时、不能后台等”，否则又是一个声明了却兑现不了的能力。现成的宿主侧实现：xacpx 的 `/later`、agent-hub 的 `wake.py`（每个参与者一个叫醒器：多次叫醒合并成一次，只交上次之后的新动态，恢复不了就新建会话）。

**“让出”能不能说清楚“别等我”**：Antigravity 的 `run_command` 有 `WaitMsBeforeAsync`（超过多久转后台）和 `IsDaemon`（声明这是常驻进程）两个参数。测试员把 `codex app-server` 当普通命令放后台、没标常驻，就一直等它结束（黑板 227 行）。宿主给了表达手段，智能体不一定会用。

**要分开问的子问题**（对应能力单元 wake-*）：能不能让出而不是阻塞干等；外部能不能看到它在等什么；等的东西到了能不能带着结果恢复会话；等的东西不来能不能被发现（Antigravity 的“让出中”标记会残留，黑板 69 行）；保管等待的一方重启后唤醒还在不在。

**对协作的意义**：没有唤醒，中心只能轮询，既烧钱又耗掉缓存；往返、汇总都要“等对方”，等待由谁保管决定了中心要不要常驻；人也是一个智能体，人的回复本身就是一种唤醒。`probe/scripts/watch_agy.js`（按会话索引判断、10 分钟无进展判卡住）是中心一侧对 Antigravity 的唤醒实现。

**还不知道**：Codex（app-server 的通知；exec 冷进程没有唤醒）、Claude Code 无头模式、OpenCode、WorkBuddy 各自有没有这几项（Hermes 原生命令行有 cron 定时，经过见 `EVALUATION_20261017.md` 末尾附，其余几项未测）；Antigravity 定时 sidecar 在桌面窗口关掉后是否照常触发；ACP 协议本身有没有表达“让出、在等什么”的方法。

## 附录：黑板里的路线编号

黑板的 `route` 字段用 `<产品>/<段>/<入口>` 记路线，段用旧代码：L0 = 各产品原生入口，L1a = ACP 桥直连，L1b = acpx，L2 = 我们的后端，L3 = 网页。例：`codex/L0/app-server`、`codex/L1a/codex-acp`、`codex/L1b/acpx`、`antigravity/L0/connect-rpc`、`*/L2/server-api`、`*/L3/console`。旧写法由 `probe/scripts/build_matrix.js` 的别名表归并。《术语表》规定不引入 L 编号，所以这些代码只留在数据里，正文一律用“网页、后端、适配器、智能体产品”。
