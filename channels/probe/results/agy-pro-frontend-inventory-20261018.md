# hub 前端全面盘点与开源对照研究报告（2026-10-18）

## 核心结论（大白话）

我们当前前端最大的硬伤不是功能太少，而是“严重的视觉拥挤”与“大量的幻觉设计”并存。页面上堆砌了近 80 处控件、7 大渠道胶囊、4 类元智能体护航总管和各种跳转抽屉，但底层真正接通的只有最简陋的一条路——调用一次性命令行拉起 acpx 命名会话。下层智能体生态其实原生支持真正的轮内插话、运行时挂起审批、原生会话接管和分支分叉，前端却一个都没接上，反而用“给大模型发一句催促文字”和“事后正则匹配报错”在界面上捏造虚假的控制闭环。两个前端页面（/console/ 与首页对话抽屉）各自硬编码了一套互不相同的模型表与开关，同一操作各调各的接口。成熟的开源智能体工作台（如 OpenHands、Cline/Roo Code、OpenCode）的核心精髓，是从不以“各家大模型品牌与旋钮”为中心塞满屏幕，而是以“当前任务、工作区沙箱、代码变更 Diff 和确定性的运行时工具拦截”为中心组织界面。我们必须彻底砍掉浮夸的元智能体外壳与重复入口，将前端收敛为一个以工作区和任务为重心的极简工作台。

## 〇、盘点概况与分类数据

本次盘点覆盖当前系统的两个主要交互页面：
1. **独立极速控制台**：`/console/`（对应代码 `console/index.html` 与 `console/console.js`）；
2. **首页对话抽屉**：`/` 对话与控制室（对应代码 `hub/js/obs/chat.js`、`hub/js/obs/trace.js`、`hub/js/obs/sessions.js` 及 `hub/js/obs/panel.js`）。
后端对接接口基于统一服务 `:8941`（`server.ts` + `gateway.ts`），下层能力真实性比照实测矩阵 `channels/probe/MATRIX.md`（938 条黑板事实）与 `channels/probe/results/zcode-glm-L3-controls.md`。

### 1. 控件分布与判定统计

全系统经去重归类后共统计 **76 组** 前端交互控件（若计入各处重复渲染位置则超过 110 个触点）。判定结果四类分布如下：

| 判定类别 | 定义说明 | 控件组数 | 占比 | 典型代表 |
|---|---|---|---|---|
| **真闭环** | 控件点击触发真实 API，后端正确执行，下层生态实测支持并真实生效，状态更新可验证 | 28 组 | 36.8% | 中止运行（Cancel）、会话历史查看、CWD 工作目录切换（P0 修复后）、本地折叠与过滤 |
| **假闭环** | 界面有反馈（Toast/状态变更/API 200），但语义严重缩水、降级，或纯属模拟（名不副实） | 26 组 | 34.2% | 审批横幅（事后正则+全放行重跑）、断点续跑（发提示词/原生落空槽）、跨渠道接力（3 轮粗暴截断摘要）、新建会话（内存草稿无落盘） |
| **死按钮** | 渲染在界面上但无任何有效点击处理（或已被 P0 紧急打补丁接上） | 4 组 | 5.3% | `/console/` 实况条待审批与运行中药丸（P0 补上跳转）、未验证渠道的模型/权限下拉 |
| **严重重复** | 同一核心功能在单页内多达 3~6 处入口，或两个前端实现两套逻辑、调用不同接口 | 18 组 | 23.7% | 新建会话（全系统 10 处）、模型下拉（两页各写死一套且抽屉内重复）、巡检（5 处）、接力（5 处） |

## 一、全量前端控件盘点表

> **判定标准**：
> - **真闭环**：UI 意图 → 接口 → 后端处理 → 下层生态实操，整条控制链语义真实兑现。
> - **假闭环**：UI 宣传的功能与下层真实发生的事情严重背离（存在幻觉、事后模拟或降级）。
> - **死按钮**：DOM 上存在该交互元素，但缺少有效事件监听或下层逻辑完全缺位。
> - **重复**：多个控件完成同一诉求，造成页面拥塞与认知困惑。

## 二、与成熟开源项目的深度对照

用户原话特别指出：“开源项目的精髓没有完全借鉴”。我们选取了国际上最有代表性、在行业内被广泛验证的 3 个顶级开源智能体工作台（加上本地参考基线 xacpx），从页面组织、功能取舍、交互精髓与底层兑现进行逐项对照：

### 1. OpenHands (All-Hands AI / 原 OpenDevin)
- **项目定位**：开源第一梯队的自主式 AI 软件工程工作台（GitHub 40k+ Stars）
- **官方仓库与证据**：[https://github.com/All-Hands-AI/OpenHands](https://github.com/All-Hands-AI/OpenHands)
- **页面是如何组织的**：
  OpenHands 采用经典的 **“任务-工作区”三栏工作台**，结构极其清晰稳定：
  - **左栏（项目与历史）**：工作区文件树（File Explorer）+ 历史任务列表（Conversations / Tasks）。
  - **中栏（交互与思考流）**：Agent 当前目标（Goal）、单步思考过程（Thoughts / Actions）与用户沟通气泡；正在执行的步骤有清晰的 Spinner，执行完毕自动收起。
  - **右栏/底栏（工作空间实况三合一）**：集成终端（Interactive Terminal，实时看命令执行）、浏览器预览（Browser VNC，看网页应用渲染）、代码变更对比（Git Diff 视窗）。
- **值得我们借鉴的核心精髓**：
  1. **以“任务/仓库”为中心，而非“智能体品牌”为中心**：用户打开 OpenHands 是为了“修一个 Issue”或“写一个模块”，工作台核心呈现的是代码仓库和任务进度，绝不会在主屏幕上密密麻麻并列摆放 7 个大模型厂牌的彩色图标和十几根断路器。
  2. **运行时挂起的人机在环审批（True Human-in-the-Loop）**：智能体在需要运行高风险 Bash 命令或修改核心配置时，不是跑完了去正则匹配，而是在执行那一瞬间由底层 Docker/Agent Runtime **暂停并抛出确认卡片**，用户点击允许后进程在同一上下文继续执行。
  3. **实时文件 Diff 可视化**：代码智能体干了什么，用户最关心的是“你改了我哪行代码”。OpenHands 右侧常驻 Diff 视图，文件改动毫秒级对比呈现；而我们的系统只有简陋的文本输出。

### 2. Cline / Roo Code
- **项目定位**：VS Code 生态中落地最深、口碑最好的开源自主编码工作台（合计 50k+ Stars）
- **官方仓库与证据**：[https://github.com/cline/cline](https://github.com/cline/cline) ｜ [https://github.com/RooVetGit/Roo-Code](https://github.com/RooVetGit/Roo-Code)
- **页面是如何组织的**：
  Cline / Roo Code 是一个**极高信噪比的垂直工作台**，界面没有任何多余的装饰性元素：
  - **顶部**：当前功能模式（Mode: Architect / Code / Ask）选择器 + 当前任务历史入口。
  - **中部**：步骤执行流。每一步严格分为 `Thinking`（折叠）、`Tool Use Request`（挂起待审批卡片）、`Execution Result`（折叠）。
  - **底部浮动操作区**：当智能体请求写文件时，自动在编辑器中弹出原汁原味的 VS Code Unified Diff 预览，并在底部浮现“Approve / Reject”操作条；对于终端命令，清晰展示完整命令行。
  - **输入框与监控**：输入框集成 Token 水位指示器（实时显示当前上下文窗口已用多少、剩余多少、预估费用），支持一键添加上下文文件。
- **值得我们借鉴的核心精髓**：
  1. **“模式隔离（Mode-Driven）”代替“渠道堆叠”**：Roo Code 绝不让用户在写代码时去手动管理 7 个智能体。它用 **模式** 来定义能力边界——Architect 模式只有只读和设计权限，不能写代码；Code 模式拥有完整工具链；Ask 模式只答疑。用户只需选“我要做什么”，权限与系统提示自动严密对齐。
  2. **写文件必须见 Diff，跑命令必须见命令行**：杜绝黑盒。智能体准备写盘前，先在内存中生成 Patch 并拉起 Diff 视图，用户审查代码行增删后才批准落盘。我们系统里的写文件全是在命令行背后偷偷执行，出错了用户都不知道改了哪里。
  3. **上下文窗口与花费绝对透明**：每一轮消耗多少 Token、命中多少 Cache、花了多少钱实时跳动显示。我们系统对当前模型上下文还剩多少毫无感知，长任务直接撞墙或被截断。
  4. **检查点快照与时光倒流（Checkpoint & Rewind）**：基于底层 Git 对每一个步骤自动做轻量提交，任何时候用户不满意，点击“恢复检查点”即可回滚代码和对话状态。

### 3. OpenCode (sst/opencode)
- **项目定位**：现代开源终端与 Web 多智能体执行中枢，原生深度支持 ACP 与主流模型厂商（GitHub 15k+ Stars）
- **官方仓库与证据**：[https://github.com/sst/opencode](https://github.com/sst/opencode)
- **页面是如何组织的**：
  OpenCode 提供 TUI 与轻量 Web 端（`opencode serve`）：
  - 界面风格极度克制，整个 Web 端就是一份精美、流式响应的工作台。
  - 顶部显示当前项目名与会话 ID；主区域清晰列出 Agent 的每一个工具调用（调用参数、耗时、标准输出）；底部输入框支持原生斜杠命令。
- **值得我们借鉴的核心精髓**：
  1. **零虚假概念，能力动态探测**：OpenCode 没有任何自封的“巡检总管”、“容灾脑会话”、“多智能体督导”等概念外壳。模型列表绝不写死在前端 JS 里，而是调用后端真实 Provider 动态返回当前已验证支持的模型。
  2. **干净的上下文治理（/compact 与 /undo）**：不搞花哨的伪接力，提供原生的 `/compact` 压缩上下文和 `/undo` 回退上一轮。
  3. **标准协议对接**：直接暴露真实的 ACP 协议方法与原生终端，不通过二次包裹丢失底层信息。

### 4. xacpx（本地已验证的优秀实践）
- **项目定位**：嵌入式 acpx 运行时的成熟宿主实现
- **值得我们借鉴的核心精髓**：
  1. **原生会话接管（`/ssn`）**：通过查询智能体磁盘目录（`~/.codex/sessions` 等），以 `(agent, cwd, sessionId)` 真实接管原生会话，为原生会话赋予可读逻辑别名，而不是像我们现在这样点原生会话却建了一个空会话。
  2. **持久化落盘队列**：临时文件写入 → 强制刷盘（fsync）→ 原子改名（rename）→ 回读校验。服务崩溃重启后自动重放队列，绝不在内存里裸跑。
  3. **真正的单会话排空锁**：严格保证同一会话任何时刻只有一个执行进程在跑，彻底消灭并发写锁冲突。

## 三、根因剖析：为什么界面如此拥挤且充满“幻觉设计”？

### 根因 1：做作的“控制感”与系统自负（用虚假功能掩盖底层粗糙）
- **表现**：系统构想了一套宏大的“多智能体治理图景”——4 个元智能体（自动批准督导、断网续跑督导、渠道容灾总管、防死循环督导），配备了“大脑切换”、“唤醒巡检”、“总监视图”、“断路器健康灯”等一整套复杂的 UI 构件。
- **实质**：底层根本没有相应的常驻守护和执行引擎支持。所谓的督导，要么是把用户的只读权限偷偷摸摸在启动时改成 `--approve-all`，要么是在报错时盲目拉起一次高成本的大模型对话（`meta-brain-supervisor`）去空转分析。**把原本应该由底层架构静默、稳定完成的基础工程（如进程保活、幂等重试、超时控制、进程锁），包装成了前台高大上的“元智能体”，本质是技术债务向前台的外溢。** 用户感觉界面复杂专业，实际一点就漏。

### 根因 2：读与控的身份彻底割裂，下层高级原语被闲置
- **表现**：用户在左侧看的是本地扫描出来的真实原生会话（如人在 Codex 桌面端创建的工作），但在右侧输入指令发送时，网关却把编号截断当成了 acpx 的名字，在后台凭空建了一个全新的空槽位。下层实测证明 Codex app-server 和 Antigravity 原生支持真正的**轮内插话（Steer）**、**中途挂起审批**、**原生会话接管**和**原生分支分叉（Fork）**，但网关全线走最简陋的一次性 `acpx prompt` 命令行。
- **实质**：既然底层高级能力没接上，前端为了交差，便开始大搞“幻觉模拟”：
  - 把“真插话”降级为“先杀掉进程再重新下发全新任务”，在按钮上强行标榜为“中断并插队”；
  - 把“真审批”降级为“进程退出后正则抓取错误输出”，在界面上伪造“允许一次/始终允许”横幅，批准动作居然是带 `--approve-all` 把任务重跑一遍；
  - 把“原生分叉”降级为“切取前 3 轮最后几百个字符的纯文本拼凑”，宣称是“无缝移交、上下文打包”。

### 3. 前后端严重割裂，硬编码驱动，不以实测为真源
- **表现**：
  - `/console/` 和首页抽屉是两个完全平行开发的前端代码库（`console.js` 2680 行，`chat.js` 2285 行）。
  - `console.js` 头部写死了一套模型表（Codex 为 `gpt-5.4`，Claude 为 `glm-5.1`）；
  - `chat.js` 头部又写死了一套完全不同的模型表（Codex 甚至出现了不存在的幻觉模型 `gpt-6-luna`，Claude 为 `sonnet`）；
  - 服务端 `:8941` 内部的 `CHANNEL_PROFILES` 又有一套自己的默认模型。
  - 前端显示哪些控件，完全由前端硬编码的布尔值决定（例如 Hermes 在下层实测支持中途切模型，在首页抽屉里却被硬编码隐藏；OpenCode 实测切模型报错，界面上却一直展示下拉框）。
- **实质**：没有落实《核心抽象》已定好的“能力登记表（Capability Matrix）”。前端不是通过 API 询问“当前渠道当前入口真实支持什么”，而是开发人员凭主观想象在代码里写死。

### 根因 4：忘却了智能体工作台的核心本职（任务与产物缺位）
- **表现**：无论是 `/console/` 还是首页抽屉，屏幕上最扎眼的都是各种彩色的大模型图标、元智能体胶囊、状态灯和多层抽屉。而一个程序员在操控代码智能体时最需要的几样东西：
  1. **智能体修改了哪些文件的代码？改动的 Diff 是什么？**（看不到，只能在文本里翻看杂乱的工具日志）；
  2. **当前智能体在哪个具体目录下执行？**（以前直接默认错乱，P0 刚修复）；
  3. **模型当前上下文用了多少百分比？还剩多少可用？**（完全没有仪表盘）；
  4. **危险命令拦截在哪里确认？**（没有预先拦截确认卡，全靠放行或者事后报错）。
- **实质**：产品视角走偏。设计者沉迷于“多智能体宏大叙事”和“拓扑沙盘操控感”，忽略了作为“AI 辅助编码工作台”最朴素的人机工效学——**少一点虚张声势的控制按钮，多一点清晰的代码与执行审计**。

## 四、重新设计提案：以任务与工作区为中心的极简工作台

根据用户的明确指示（“甚至允许你重新设计”），我们推翻现有的两套臃肿前端，提出**全新单页面工作台设计方案（或首页抽屉复用的同一核心组件）**。

### 1. 重构四项铁律（设计原则）
1. **彻底拔除“元智能体护航”幻觉**：前端不留任何所谓巡检总管、容灾大脑等虚构构件。自愈、重试、看门狗全部退回后台作为静默的基础设施运行。
2. **消灭两套会话身份**：彻底执行统一身份 `(channel, entry, nativeSessionId)`，左栏看到的会话就是右栏操作的会话；无法接管的原生会话明确标注“只读回放”，严禁悄悄退化为空白新会话。
3. **能力严格按 MATRIX 动态呈现**：前端模型列表与控制按钮 100% 由后端根据实测矩阵动态下发，禁止在前端硬编码模型名单与功能开关。
4. **以“工作区 + 任务 Diff”为核心视窗**：给代码变更（Diff）和真实终端输出提供一等公民视窗。

### 3. 核心布局模块说明

1. **顶部状态条（极简且真实）**：
   - 仅显示当前工作区路径、后端真实连接状态、当前会话模型的真实上下文水位（如 `Context: 42,100 / 128,000 (33%)`）。砍掉虚浮的双模式切换、星空大画布链接和各种角标。
2. **左栏（统一会话管理）**：
   - 顶部只有一个显眼的 `+ 新建任务会话`。
   - 分区显示：**受管活动会话** 与 **检测到的原生会话**。
   - 原生会话卡片上清晰标注接管状态（支持接管的提供“接管并继续”，不支持的明确标为“只读归档”，彻底杜绝误跳入同名空房间）。
3. **中栏（交互执行流）**：
   - 彻底废除事后正则匹配横幅。在智能体请求敏感操作时，由下层真正的拦截回调在此处弹出一等公民的**挂起审批卡片**（展示确切命令行、拟修改文件的 Diff），支持键盘快捷键确认。
4. **右栏（产物与变更审计视窗）**：
   - 放弃“跨渠道接力”和浮夸的“遥测Tab”，替换为对开发者真正有价值的 **Git Diff 查看器** 与 **实时终端输出日志**。智能体改动了哪一行，右侧一目了然。
5. **底栏（统一 Composer）**：
   - 整合所有参数：**执行模式**（架构只读 / 完整编码 / 纯问答）、**执行渠道与模型**（下拉框直接由服务端实测可用列表驱动）、**工作目录**。
   - 只有三个清晰的动作按钮：空闲时为 `🚀 下发指令`；执行中根据底层实测能力动态显示：支持真插话的展示 `⚡ 轮内插话`，支持打断的展示 `⏹ 立即打断`。

### 4. 必须彻底废除的功能与视觉清单（砍掉这 14 样东西）

| 序号 | 废除项名称 | 原先在哪 | 为什么必须坚决砍掉 |
|---|---|---|---|
| 1 | 4 类元智能体护航总管及胶囊 | `/console/` 护航页、首页抽屉状态条 | 纯属概念外壳与幻觉设计，不仅不能自愈，反而在后台空转烧 Token、静默升级权限 |
| 2 | “唤醒巡检”按钮（全系统 5 处） | 两页顶栏、命令面板、抽屉、左栏 | 用户不需要反复手动“巡检”智能体，智能体死活应由进程守护与状态探测自动处理 |
| 3 | “换脑日志与脑会话” (`meta-brain-supervisor`) | 首页抽屉元智能体条 | 让用户去操心“哪个模型给巡检当大脑”，属于典型的把实现细节暴露给用户的恶劣设计 |
| 4 | 事后正则审批横幅与卡片 | `/console/` 横幅、看板卡片、抽屉横幅 | 事后生成的假审批，点击是带 `--approve-all` 从头重跑，误导性极大且极不安全 |
| 5 | “跨渠道无缝接力”面板与 @提及接力（共 5 处） | 右抽屉、对话头、输入框、快捷词 | 实际只是截断为几百字的纯文本摘要，既非真分叉又丢失状态，属于虚假包装 |
| 6 | 伪“断点续跑”（共 3 处） | 对话头、抽屉胶囊、快捷词 | 只是发一句催促文字，且会导致原生会话接错路掉入空房间；应由底层接管机制静默取代 |
| 7 | 伪“中断并插队/中断并立即发送” | 输入框底部 | ACP 下无轮内插话时只是暴力打断重发，直接保留单纯的“打断”和“发送”即可 |
| 8 | 内存队列条与伪排队 | 输入框上方 | 内存队列重启即失，没有持久化落盘支持的排队只会让用户丢失已输入的宝贵提示词 |
| 9 | 抽屉内的双重模型下拉框 | 抽屉头部 + 输入框上方 | 同一个抽屉内放上下两个下拉框，选项还互不相同，视觉与逻辑极度混乱 |
| 10 | 前端写死的候选模型列表 | `console.js`、`chat.js` 头部 | 包含不存在的幻觉模型（如 `gpt-6-luna`），且与后端实际挂载的模型渠道严重冲突 |
| 11 | `/console/` 与抽屉各一套前端代码库 | 全仓库 | 两套前端分别 2680 行和 2285 行，约定不一、相互割裂；必须收敛为单一核心组件 |
| 12 | 遍布各处的 10 处“+新建会话” | 顶栏、看板、左栏、抽屉等 | 收敛为左栏顶部唯一的“新建任务”按钮 |
| 13 | 协作看板视图（只读搬运版） | `/console/` 中间 Tab | 现有的看板只是把内存里的会话机械地分了 4 列，卡片点进去还是假闭环，缺乏真正的任务卡片属性 |
| 14 | 复杂的 7 渠道健康灯与彩色胶囊矩阵 | 左栏顶部 | 用户心智应当是“挑一个擅长此任务的智能体”，而不是随时盯着 7 个渠道的断路器仪表盘 |

### 2. 读层背景扫描阻塞实测证据
```text
命令: curl.exe http://127.0.0.1:8941/api/health
时间: 2026-10-18T02:42:09+08:00
耗时: 32.8 秒 (导致前端请求严重挂起)
原始输出片段:
{"ok":true,"contract":"0.2","scanning":true,"sessions":1051,"viewer":true,"search":{"done":1051,"total":1051,"running":false,"steps":194685},"roots":[...]}
```
**证据分析**：
读层在启动时扫描了本机 8 个根目录、1051 个历史会话、194,685 个步骤。在扫描期间 Node.js 单线程密集做文件 I/O，导致前端任何 API 均出现长达 30 秒的假死卡顿。这是用户频繁感到“前端慢、卡死、没有反应”的重要底层诱因之一。

### 3. 测试会话与审计声明
在本次调研与代码盘点过程中：
- 所有针对代码与前端结构的比对分析均基于静态语法树提取与只读检查；
- 针对运行中服务 `:8941` 的探测均为只读 GET 请求（`/api/gateway/state` 与 `/api/health`）；
- **本轮盘点未在任何渠道拉起带有副作用的对话，未新建任何测试会话，未触碰或开启任何后台桌面应用，未连接或读取 AP-Vibe 数据库。**
