- “认知上必须能够看到最广，才能够做的高效，而不是重复造轮子，很多东西底层就应该摸清楚。”
- “我们所有智能体都是全权限运行。”

## 我的理解（总负责人 Claude；这是我的理解，不是用户的话）

整个项目拆成几块并行，你负责“一轮之内”这一级上能力最全的那条适配路线。Codex 现在经 acpx 走 codex-acp：每一轮起一个进程，不能插进当前这一轮，不能分叉、压缩，中途换模型也没证实。`codex app-server` 是常驻的 JSON-RPC 服务，这几样它都有（`channels/README.md`“各产品的入口”一节写了 Codex 的几种入口）。上一代项目 `E:\program\GIT\Agent\agent-hub\src\agent_hub\codex_app.py`（363 行）已经用 Python 跑通过它。不要从零写，先在本机把它跑起来看清协议，再决定怎么搬。

你只写新文件：驱动放在 `trace/apps/cli/src/drivers/`（新建），测试脚本放在 `channels/probe/scripts/`。接进后端（`gateway.ts`、`server.ts`）这一步不归你：那两个文件现在由另一个对话在改。你在汇报里写清接法（在哪里调用、需要产品表加什么路线），由总负责人或那个对话接。产品表、动作表（`hub/data/`）也归总负责人，你要加的路线写成建议。

## 要回答的问题

经 app-server，Codex 能在我们这里做到哪些单元：新建、恢复、插进当前这一轮、打断、分叉、压缩、中途换模型、审批（一轮之中挂起等人答）、读每一步的事件流。每一项做得到还是做不到，凭什么（协议方法名和实测输出）。

## 已知事实

- 先读 `channels/README.md` 的“立体认知”和“管线”两节，用词照“用词”。`node hub/tools/agent_gateway.js tables` 打印产品、动作、单元 → 动作。
- `channels/hosts/codex.md` 和 `channels/hosts/codex/` 四册写了 Codex 的入口和已知的坑；黑板 `channels/probe/blackboard.jsonl` 里 route 以 `codex/L0/app-server` 开头的行是以前的实测。
- Codex 的会话记录在 `~/.codex/sessions/`；桌面端开着的会话有写锁，不要去抢人正在用的会话。
- 渠道：Codex 走代理 `http://127.0.0.1:7892`（环境变量 HTTP_PROXY、HTTPS_PROXY）。

## 还不知道的

- 本机的 codex 版本里，app-server 的方法名和事件跟 agent-hub 写的时候是否一样。
- 一个常驻的 app-server 能同时托管多少个会话，崩了怎么恢复。
- 审批挂起的时候，外部用什么消息答复。

## 怎样算真正做成

- 用一个 `probe-` 开头的新会话，真实跑一遍：新建 → 跑一轮 → 在这一轮进行中插一句话并看到它被这一轮采纳 → 打断 → 分叉出一个新会话 → 压缩 → 换模型再跑一轮。每一步在黑板追加一行（route `codex/L0/app-server`，带请求、响应摘要、日期、codex 版本）。脚本内部打印成功只算中间证据，要有 Codex 自己的会话记录或事件为证。
- 汇报写进 `channels/probe/results/codex-app-driver-20261018.md`：每个单元做得到吗、凭什么；驱动的文件和用法；接进后端的接法建议；产品表要加的路线（每个动作的实际命令或方法）。
- 打不通的如实写：哪一环通了，哪一环断了，断在什么条件下。

## 规矩

全权限运行；不提交、不推送。不杀、不重启用户的桌面应用，不往人正在用的会话发消息。改动带反斜杠、换行的代码，用编辑工具，不在命令字符串里拼。
