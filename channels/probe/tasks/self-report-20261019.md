# 问各家：这些能力你自己有没有（10-19）

## 用户的原话

> “其实每家生态都可以问一问他们有没有这些功能，比如其实有些生态他们的那个 Computer Use 会做的很好，豆包的 Computer Use 就做的很好。”
>
> “建立清晰的认知，所有的能力单元，注册表维护，打通闭环，然后稳步拓展……最终用所有方法打通尽可能多的能力单元”

## 这是我的理解

我们给每家产品维护了一张能力矩阵：127 个能力单元，每个单元在每家的四个位置（桌面端界面、原生接口、我们的适配器与后端、网页）上能不能做。数据在 `channels/probe/capability-matrix.json`，单元的定义和判据在 `hub/data/capability-units.json`（`definition`、`judge` 字段）。

很多格子还是空的或未证实，尤其是你自己这家的原生接口和桌面端界面两列。这些都是从外面摸索出来的。你是这家产品里的智能体，对自己有哪些工具、命令、设置、界面功能，可能比我们从外面看得更清楚。

## 要回答的问题

就你自己这家产品（你运行在其中的那个应用或命令行）：

1. 矩阵里你这家的格子，哪些你原生就能做？入口是什么（命令、接口、工具名、界面上的位置）？怎样能验证？
2. 有哪些能力是我们清单里没有、但你这家有、而且对多智能体协作有用的？比如操作电脑或浏览器（Computer Use）、内置的多智能体并行、定时任务、长期记忆、回看历史对话等。

## 已知

- 你这家的格子：在 `capability-matrix.json` 的 `units[].cells.<你的产品 id>` 里，`app`、`api`、`adapter`、`front` 四个位置的值是 pass / partial / unverified / fail / null。null 是没有任何记录。
- 产品 id：claude、codex、antigravity、zcode、workbuddy、opencode、hermes。
- 10-19 有一家把 30 格报成“能做”，核下来只有 7 格有实际调用的证据。所以每条说法都要写清依据是什么：是你实际试过（写命令和结果），还是看到工具列表或文档，还是推测。

## 还不知道

你这家到底还有哪些我们没摸到的能力、入口和限制。

## 怎样算做成

- 写一份报告：`channels/probe/results/self-report-<产品 id>-20261019.md`。
  - 第一部分逐条列能做的单元：单元 id、入口、依据（试过 / 看到 / 推测）、怎样验证。
  - 第二部分列清单外的新能力：叫什么、做什么、入口、依据。
  - 第三部分列你确定做不到的，并写明理由。
- 不往黑板写：自报是线索，后面会另派人照判据实测。
- 能顺手试的，就在 `probe-` 开头的会话或临时目录里试一下，把命令和结果写进报告。
- 最后交回一句话：写了多少条、其中试过几条、发现了哪些清单外的能力。

## 不能碰的

- 不改 `trace/`、`m/`、`hub/` 下的代码，不改全局配置和凭证。
- 不对用户正在用的会话发消息、改名或删除；不杀桌面应用。
- 报告和回复里不写明文密钥。
