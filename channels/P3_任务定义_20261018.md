## 1. 任务

做一个“acpx 运行时驱动”：在后端里通过 acpx 的库接口（`acpx/runtime`）新建会话、恢复会话、跑一轮、看事件、打断、关闭会话、答复审批，替换现在“每做一步就拉起一个 acpx 命令行子进程、再解析它的输出”的做法。范围是经 ACP 的六家（Claude、ZCode、WorkBuddy、OpenCode、Hermes，以及暂时仍经 ACP 的 Codex）。命令行做法保留，作为回退。

做成的标志：前端的“新建会话、恢复会话、打断、审批”四件事，对这六家都按实测可靠工作；审批是在一轮中途真的问人，而不是事后正则匹配再全放行重发。

## 2. 背景

**现状。** 后端（`gateway.ts`）每做一步就用子进程调一次 acpx 命令行，从它的标准输出里一行行解析事件，再靠退出码、错误帧和文件轮询猜这一轮成没成。本轮修复（评估文档第十一节）已经把“成没成”改成看 stopReason，新建会话和恢复会话在四家上复测通过，但这种做法的几个病根还在：
- 审批是事后的：这一轮结束后用正则在输出里找“权限被拒”，再带全放行参数重发（评估文档附录 A 第 4 条）；
- 排队在后端内存里，服务重启就丢（第 9 条）；
- 同一个会话的命令行和后端各自拉进程，状态不共享；
- 每一步一个新进程，慢；Codex 新建会话要几分钟（原因在查）。

**用户的设想（原话）。**
- “我们系统能正常跑起来最重要，然后才是拓展，我们为了达到baseline不应该做那么多，而是在baseline的基础上做我们的东西”
- “我感觉我们没有借鉴开源项目吧，开源项目比如acpx对于这些渠道应该有很成熟的baseline了吧”
- “【两个都做，分先后】是决策的”：先做 P3（借 acpx 运行时把新建会话、恢复会话、打断、真审批做稳），再做 P3b（Codex app-server、Antigravity 的原生插话、分叉）。

**走过的路。** 10-17 我曾写过一份 P3 规格交给 Codex，用户指出我没把我们的抽象和 acpx 的抽象逐项比对就开始替换，那份规格作废。之后做了逐项对照（评估文档 7.1），又读到我们自己早有的适配器设计和 agent-hub 驱动（第十节）。

**外面的现状。** acpx 0.19.5 导出可嵌入的运行时：`ensureSession`（新建或恢复会话，可带原生会话编号）、`startTurn`/`runTurn`（按顺序交出这一轮的事件和结束原因）、`cancel`、`close`、`setModel`/`setMode`、`onPermissionRequest`（一轮中途的审批回调）、`createSharedAcpRuntime`（应用和命令行共用同一个会话主进程，排队也在里面）。xacpx 就是嵌入它做的，并补了持久队列、审批策略、定时唤醒、接管原生会话。

## 3. 抽离出的议题

离开本项目，这是“**宿主怎样可靠地驱动一个外部智能体进程**”的问题：会话由谁持有、一轮的生命周期怎样观察、中途的审批怎样交回给人、进程崩了怎样恢复、多个调用方怎样不打架。在外面，编辑器接智能体（Zed、JetBrains 的 ACP 客户端）、聊天机器人桥（xacpx 接微信和飞书）、任务编排器都在解这个问题。我们自己的《适配器模块设计》§3（适配协议和语义规则）、§5（所有权）、§8（权限与审批）就是对它的回答，P3 是把其中一部分落成代码。

## 4. 思考（负责人的想法，可以推翻）

- **只借四样，不多借。** acpx 运行时覆盖会话管理、跑一轮、事件流、审批四件事（评估文档 7.1 的结论）。插话、分叉、压缩上下文、额度、唤醒、接管原生会话的身份统一，它要么没有、要么不够，P3 不碰，留给 P3b 和以后。
- **驱动放进单独的工作进程。** 理由：智能体进程崩溃或卡住时不拖垮后端主进程（10-17 已经见过启动时主线程被同步扫描卡住）；也和 xacpx“每个会话一个工作进程、防崩溃循环”的做法一致。代价是多一层进程间通信。
- **驱动接口按我们的能力单元起名**，不按 acpx 的名字：新建会话、恢复会话、跑一轮、打断、关闭会话、答复审批。以后 P3b 的 Codex app-server 驱动、Antigravity 驱动实现同一个接口，后端只认这个接口。这就是《适配器模块设计》说的“能力清单 ＋ 接口面”：同一个能力，不同的接口面。
- **审批默认放行智能体写它自己的数据目录。** WorkBuddy 在只读权限下要写自己的记忆文件，被拒后整轮没有回复（评估文档第十一节）。这类请求应自动批准；其余写操作在只读模式下转给人。判定顺序照 xacpx：自动拒、自动批、上报给人、默认；出错一律拒；审批只对发起它的那一轮有效。
- **风险。** 一是 acpx 运行时的接口在 0.x 版本，可能变，所以要钉住版本、只在一个模块里引用它；二是命令行和后端共用会话主进程以后，人在终端里用 acpx 的同名会话会和后端排队，要在界面上看得出来；三是 Codex 经 ACP 本来就弱（只能排到下一轮），P3 只求它“新建、恢复、打断、审批”稳定，强能力等 P3b。

## 6. 调研

- 要调研，但范围小：acpx 运行时和 xacpx 的源码已在本机，第 1 步读它们即可，不需要再上网找别的框架。
- 正在并行的一项调研会影响 P3：Codex 新建会话为什么要几分钟（交给了 Antigravity，结果写在 `probe/results/agy-pro-codex-slow-open-20261018.md`）。如果根因在 codex-acp 桥本身，P3 也救不了 Codex 的速度，就要把 Codex 提前到 P3b 走 app-server。
- 后端架构的整体缺陷分析也在并行（`probe/results/agy-pro-backend-architecture-20261018.md`），它可能改变驱动该放在哪里。

## 7. 需要人判断的地方

1. **在 trace 工作区加 acpx 依赖**（`acpx@0.19.5`，npm 安装，与本机全局版本相同）。这是新增依赖，按规矩要你同意。
2. **审批默认自动放行“智能体写它自己的数据目录”**（例如 `~/.workbuddy/`、`~/.zcode/`、`~/.claude/projects/`），其余写操作在只读模式下转给你。这个放行范围要你认可。
3. **命令行和后端共用会话主进程**：好处是会话状态一致，代价是你在终端里用 acpx 同名会话时会和后端排队。要不要共用，你定；我倾向共用。

## 8. 假设

- acpx 0.19.5 的运行时在 Windows 上和命令行一样能拉起各家的桥（命令行已实测能，运行时未测）。
- 各家 ACP 桥的审批请求格式一致，运行时的回调能拿到足够的信息（工具名、目标路径）来判断“是不是写它自己的数据目录”。
- 现在的复测脚本（`probe/scripts/P0/verify_open_resume.js`）足以作为第 3 步的验收；审批需要新写一个验收脚本。

## 附：第 1 步的接口对照（2026-10-18，读 acpx 0.19.5 `dist/runtime.d.ts`、`session-options-*.d.ts`）

| 我们的能力单元 | acpx 运行时 | 说明 |
|---|---|---|
| 新建会话 | `ensureSession({sessionKey, agent, mode: "persistent", cwd, sessionOptions})` → 句柄 | `sessionOptions` 只在第一次新建时生效（系统提示词定死在新建那一刻） |
| 恢复会话 | 同一个 `sessionKey` 再 `ensureSession`；接管原生会话时带 `resumeSessionId` | 要该家的桥支持加载会话 |
| 跑一轮 | `startTurn({handle, text, mode: "prompt", requestId, timeoutMs, onPermissionRequest})` → `events`（异步迭代）＋ `result` | `result` 三态：completed、cancelled（都带 stopReason）、failed（带 code、retryable）。直接替代我们的 `judgeAcpxTurn` |
| 观察·实时 | `events`：`text_delta`（输出或思考）、`tool_call`（带状态、路径、输入输出）、`status`（用量、计划条目、可用命令）、`done`、`error` | 替代我们逐行解析 NDJSON |
| 观察·历史 | 无直接方法；共享运行时有 `watchSession({cursor})` 可从某个位置往后读事件日志 | 历史还是靠只读旁路读会话文件 |
| 状态识别 | `getStatus` → 模型、用量、可用命令、最近一次请求编号 | 没有“工作中、等审批、在等什么”，要我们自己从事件里推 |
| 打断 | `cancel({handle})`，或这一轮的 `turn.cancel()` | |
| 关闭会话 | `close({handle, reason, discardPersistentState})`；`prepareFreshSession` 让下一次新建全新会话 | |
| 答复审批 | 运行时级 `onPermissionRequest`，或每一轮单独传；回调拿到 `sessionId`、原始请求、推断的工具类别（读、改、删、执行、取网等），返回 `allow_once`、`allow_always`、`reject_once`、`reject_always`、`cancel`；回调返回空或抛错就按 `permissionPolicy` 处理 | `permissionPolicy` 有 `autoApprove`、`autoDeny`、`escalate` 三张规则表和默认动作，判定“写它自己的数据目录”可以在回调里看请求里的路径 |
| 向人提问 | `onElicitation`（表单或网址两种） | 对应能力单元 ask-user |
| 切模型、切模式 | `setModel`、`setMode`、`setConfigOption`；`inspectAgentModels` 不建会话就能读模型列表 | 模型不支持时抛 `RequestedModelUnsupportedError` |
| 插话 | 不支持。进程内运行时把 `mode: "steer"` 排在当前轮后面（等于“下一轮”），共享运行时直接拒绝 | 原文注释：ACP 没有轮内插话请求 |
| 分叉、压缩上下文、额度 | 不支持 | 留给 P3b 和渠道层 |

**读接口时发现的三件事，会改设计：**
1. **环境变量是按运行时给的，不是按会话给的。** `agentProcessEnv` 在创建运行时那一刻固定下来。而我们每家要的环境变量不同（WorkBuddy 的两个变量、Claude 从 `settings.json` 取的供应商变量），所以要么每家一个运行时实例，要么给每家的启动命令包一层。我倾向每家一个实例，正好也和“每家一个工作进程”对上。
2. **权限可以按会话定。** `sessionPermissions` 回调在建立或重连会话时，按会话的身份（目录、命令）返回权限设置，这样前端给每个会话选的权限模式能真正落到这个会话上。
3. **共用命令行的会话主进程（`createSharedAcpRuntime`）时不能插话、也拿不到进程内的审批回调以外的控制**：它连的是 acpx 命令行的本地主进程，控制要经那个进程转。第 7 节第 3 个问题（要不要共用）因此更要你定：共用的好处是你在终端里用 acpx 看得到同一个会话；不共用（进程内运行时，会话记录另放一个目录）控制更完整。
